## §2 项目开场白（STAR 浓缩版）

> **S 场景**：我自己在用各种日程和待办工具时发现两类问题——AI 生成的日程时间算错；更隐蔽的是两件事在日历上不重叠，但从上一个地点开车到下一个地点根本来不及。
> **T 任务**：我想做一个真的能用的 Agent 日程助手，而不是只能演示的 demo。
> **A 行动**：
> 1. 先把"谁能改数据"这件事管住：37 个工具分 none / auto / confirm 三级确认等级，危险操作必须用户点确认。
> 2. 再把"算得准"这件事独立出来：写一个不依赖模型的规划引擎，纯 Python 贪心 + OR-Tools CP-SAT 深度优化，同输入同输出。
> 3. 再把"出错了怎么办"补上：多步执行用快照补偿事务，模型异常分三类分别处理，加指数退避和本地规则降级。
> 4. 最后建立反馈闭环：持久化执行轨迹 + 隔离 DB 的端到端评测页，把"感觉能用"变成可量化的数据。
> **R 结果**：220 个自动化测试全绿；5 个评测场景能跑出工具选择正确率、约束通过率、确认安全性三个指标；整个系统只依赖 6 个第三方库，前端零框架零构建，本地跑起来就能用。

## §3 技术深挖题

### 3.1 整体架构

#### Q1. 讲一下你的整体架构。

**答**：

```
frontend (原生 JS, 零构建)
    ↓ HTTP/JSON
FastAPI routes (app/api/)
    ↓
services (app/services/)  ← 事务边界、锁定、版本快照、撤销
    ├──────────────┬──────────────┐
    ↓              ↓              ↓
Agent 编排       规划引擎        外部集成
app/agent/      app/planning/   app/integrations/
  loop/agent     engine(贪心)     maps(高德)
  memory         optimizer(CP-SAT) weather(Open-Meteo)
  confirmation   windows
  transaction
    ↓
tools (app/tools/, 37 个)  →  services  →  SQLAlchemy → SQLite
    ↑
skills (app/skills/, 10 个) 负责意图路由 + 工具白名单
    ↑
llm (app/llm/) mock + openai_compat
```

三条主线值得说：
- **Agent 线**：`loop.py` 是决策循环，`agent.py` 是门面（组装 Loop / Memory / Confirmation / Skills），`transaction.py` 是补偿事务，`confirmation.py` 是待确认操作的持久化。
- **规划线**：`engine.py` 是纯 Python 贪心规划器，`optimizer.py` 是 CP-SAT 求解器，`windows.py` 算可用时间窗。**这条线不 import 任何模型、不碰数据库**。
- **工具线**：`tools/` 下按领域分 11 个模块，`registry.py` 统一执行入口。

**追问预案**：
- *"为什么 service 层和 tool 层都存在？"* —— tool 是"能力单元"，对外暴露 schema 供 LLM 选择；service 是"业务规则"，对 REST API 和 tool 都复用。放两边的判断标准是：**这条规则是否与"谁在调用"有关**。比如"任务完成后同步取消它的排期"是业务规则，两边都要用，就放 service；"把任务标题转义"是接口层的事，就放 tool。
- *"怎么保证规划引擎不碰数据库？"* —— `app/planning/engine.py` 和 `optimizer.py` 的 import 只有 `datetime` / `typing` / 自己的 dataclass，没有任何 ORM 或 service 的引用。数据由 service 层以 `PlanTask` / `PlanAssignment` 这种纯数据类传进去。这带来三个好处：可单测、可复现、可换优化器。

### 3.2 LLM 与确定性引擎的边界

#### Q2. 为什么不让 LLM 直接排期？多写几千行值得吗？

**答**（这题是全场的核心，必须答得清楚）：

大模型排期失败有三种模式，不是"不够聪明"，是**机制上不可靠**：

1. **算术不可靠**：跨越时区、夏令时、午休窗口的加减，LLM 出错率很高，而且错了自己不知道。
2. **不可复现**：temperature 采样 + 上下文顺序影响，同一请求两次结果不同。做日程的用户会直接失去信任。
3. **无约束保证**：模型不知道"你必须预留 40 分钟通勤"，它只会给一个看起来合理的答案。

所以我的切分是：
- **LLM 负责"软"的部分**：理解自然语言、判断意图该调哪些工具、把结构化结果翻译成人话。
- **引擎负责"硬"的部分**：算可行时间窗、做区间避让、满足依赖、跑 CP-SAT 求全局最优。

**值得吗？** 我的判断是值得，因为这个项目的价值恰恰不在"模型很聪明"，而在"**结果可信**"。一个不能保证不排冲突、不能复现、不能解释为什么这么排的日程助手，是不能真的拿来用的。代价是多了几千行代码，但换来的是：引擎可以独立单测（同输入同输出，可以写断言），模型换了不影响排期结果，排期逻辑可以独立演进。

**追问预案**：
- *"那 LLM 会不会因为不知道细节而做出错的决定？"* —— 会，所以系统不把正确性押在 LLM 的判断上。LLM 选错工具（比如本该用 `create_events` 却用了 `generate_plan`），工具层的确认等级和 `system_hint` 会拦住；生成出来的日程还要过 `check_conflicts` 和执行后审计（`postflight_audit`），发现冲突会回滚并告诉用户。**LLM 的错误是"可检测、可拦截"的，而不是"静默污染数据"的。**
- *"这不就是把 LLM 降级成个 dispatcher 吗？"* —— 是的，但这是刻意的。Dispatcher 做好了也是有价值的工程：意图到工具的映射、多轮上下文管理、参数校验、失败恢复，这些恰好是 Agent 落地时最脏的部分。而且我保留了"LLM 做决策"的路径——`compare_plan_alternatives` 返回三套方案让 LLM 解释取舍，`analyze_plan_risks` 的建议也是 LLM 组织的。**能用规则做的绝不让模型猜，能让模型做的绝不用规则硬编码。**

#### Q3. 什么是"确定性"？具体怎么保证的？

**答**：
- 规划引擎**不 import 模型、不访问数据库**，输入是纯数据类（`PlanTask` 列表、忙碌区间列表、时间窗列表），输出是 `PlanResult`。
- 同一份输入 → 同一份输出，没有随机性、没有时间依赖（时间由参数传入而非内部取 `now()`）。
- 贪心路径的排序键 `_sort_key` 是全序（固定日程在前，然后按 `planning_weight` 降序，再按截止时间），不会有并列项导致的不稳定。
- CP-SAT 路径有 5 秒 time limit，`num_search_workers=1`（单线程求解保证确定性），固定 seed 行为由单线程 + 固定模型保证。
- 结果是**可断言的**：测试里可以直接写"这个任务必须在第 2 天上午"，而不是"结果里应该包含某个任务"。

**追问**：
- *"CP-SAT 是确定性的吗？"* —— 严格说，CP-SAT 内部有启发式搜索，理论上多线程下不保证完全确定。所以我设了 `num_search_workers=1`。而且即使求解器返回不同的最优解，**结果仍然是"满足全部约束的最优解"**——同分最优解之间差异不影响正确性。这跟贪心的"必须逐字节相同"是两种不同的确定性保证。

### 3.3 Tool Calling 与 Agent 编排

#### Q4. Tool Registry 是怎么设计的？

**答**（`app/tools/base.py` + `registry.py`）：

每个工具是一个 `Tool` 子类，声明五样东西：
- `name` / `description` —— 给 LLM 看
- `input_schema` / `output_schema` —— JSON Schema，给 LLM 看
- `confirmation` —— 三档：`none`（只读）/ `auto`（可逆写）/ `confirm`（破坏性，必须用户确认）

`ToolRegistry` 负责三件事：
1. **汇总 schema**：`schemas()` 把所有工具转成 OpenAI function-calling 格式，一并塞给 LLM。
2. **统一执行入口**：`execute(name, args, db)`。所有工具异常在这里被吸收成 `ToolResult(success=False, error=...)` —— **Agent loop 永远不会被一个工具的异常打断**。
3. **统一预览入口**：`preview(name, args, db)`，`confirm` 级工具在真正执行前先给用户看"要做什么"。

**追问**：
- *"为什么要分 confirmation 三档？"* —— 不是所有写操作都需要打断用户。`generate_plan` 产生的是 `proposed` 状态，用户不点确认它也不会进正式日程，这种是 `none`；`update_task` 可逆，是 `auto`；`delete_events` 不可逆，是 `confirm`。分级依据是**"出错了代价多大"**和**"能不能撤销"**。项目里还有个更硬的保护：计划版本快照 + `undo_latest_plan`，能撤销的操作即使误触也有兜底。
- *"schema 怎么防止 LLM 传错参数？"* —— 工具内部用 Pydantic model 校验（如 `EventCreate`），校验失败会被 registry 吸收成失败结果回传给 LLM，LLM 看到错误信息可以自我修正重试。同时 `input_schema` 里带 `maxItems` / `minimum` / `maximum` 约束，减少模型生成越界参数的概率。

#### Q5. 你的 Agent Loop 是怎么跑的？

**答**（`app/agent/loop.py`）：

一次 `run()` 的流程：
1. 记下用户消息到 Memory
2. **Skill 路由**：`skill_registry.select(message)` 命中关键词后选一个 Skill，拿到它的 `allowed_tools` 白名单和 `system_hint`
3. 构建消息：system prompt（23 条规则 + 时区说明 + 偏好快照）+ 裁剪后的历史
4. 循环最多 `MAX_ITERATIONS = 12` 轮：
   - 调 LLM，拿到 tool_calls
   - 逐个处理：未知工具 / 重复调用 / 超预算 → 回传错误给 LLM；`confirm` 级工具 → 收集起来统一走一次确认；其余 → 直接执行
   - 把 Observation 结构化回传给 LLM
5. LLM 返回纯文本 → 结束
6. 迭代超限或工具调用超预算 → 走 `_finalize_without_tools`，明确告诉模型"禁止再调工具，用已有结果总结"

**关键设计**：
- **同轮多个 confirm 工具合并成一次确认**。用户点一次"确认"，不是点五次。
- **重复调用检测**：`_call_key` 是 `json.dumps(name + arguments, sort_keys=True)`，同样的工具同样的参数只执行一次，第二次直接回错误让模型别转圈。
- **工具级预算**：`TOOL_CALL_LIMITS` 逐工具限制。`check_conflicts`、`evaluate_plan` 这类只读工具限 1 次；`generate_plan` 限 2 次；`estimate_travel_time` 可以到 12 次（多段行程要算多段）。
- **Observation 压缩**：`_compact_tool_payload` 对嵌套深度限 7、列表限 8/30 条、字符串超 1200 字符截断，防止工具返回大结果把上下文撑爆。

**追问**：
- *"重复调用检测会不会误杀合法操作？"* —— 会，所以用 `seen_calls` 而不是"只允许调一次"。比如"重新规划一次再改参数"是合法的（参数不同 → key 不同 → 不算重复）。我观察到的真实误杀场景是模型卡在同一个循环里，这正是要拦的。
- *"为什么 MAX_ITERATIONS=12？"* —— 经验值。正常的"查任务 → 生成计划 → 总结"是 2–3 轮；多段行程是 5–8 轮；12 轮足够覆盖最复杂的场景，再多就说明模型在转圈，早点止损比让它跑满更好。
- *"循环超了会怎样？"* —— 不会报错，而是走"无工具总结"路径，明确要求模型基于已有结果给结论。这样用户至少拿到一个基于真实数据的回答，而不是一个 500。

#### Q6. Skill 是什么？和直接写 system prompt 有什么区别？

**答**（`app/skills/`）：

Skill 是一份 **提示词档案 + 工具白名单**，包含 `name` / `description` / `keywords` / `system_hint` / `allowed_tools` / `priority`。目前 10 个：任务理解、日程规划、冲突解决、重排、日规划、日期推荐、风险体检、多方案对比、旅行规划、天气规划。

选择逻辑（`SkillRegistry.select`）：按关键词命中数排序，排序键是 `(priority, 命中关键词总长度, 命中个数, -注册顺序)` —— 优先命中更多、更具体的技能。

**和纯 system prompt 的区别**：
1. **工具白名单是硬隔离**。选中 `date_recommendation` 后，模型只能看到那 9 个工具的 schema。这减少了可选项，降低选错工具的概率，也缩短了 prompt。
2. **提示词按场景分发**。system prompt 里的 23 条规则是通用规则（时区怎么转、区分 Task/Event/Schedule）。场景专属的细则放在对应 Skill 的 `system_hint` 里，只有该场景才注入。比如"多地点连续日程不得调用 generate_plan"这条只在旅行规划 Skill 里注入。
3. **可测试**。每个 Skill 的 `allowed_tools` 是可断言的列表，测试里直接校验"日期推荐场景不允许出现 generate_plan"。

**追问**：
- *"关键词匹配会不会漏？"* —— 会。漏了就退回通用模式（`selected_skill is None`，所有工具可见 + 完整 system prompt），功能不受影响，只是 prompt 长一点。后续可以换成 embedding 相似度路由，但当前 10 个场景关键词命中率够用，引入模型路由反而多一个不确定性。
- *"白名单会不会挡住必要工具？"* —— 会，所以我给每个 Skill 的 `allowed_tools` 配得比较宽（比如 `plan_alternatives` 允许 `get_tasks` / `get_events` / `get_schedules` 三个读取工具）。原则是**只挡"这个场景绝对不该用"的**，不追求最小集。

### 3.4 可靠性工程（这块最能体现工程能力，务必准备透）

#### Q7. Agent 死循环怎么防？

**答**（四层，从外到内）：

1. **迭代上限**：`MAX_ITERATIONS = 12`，超了强制收尾。
2. **工具调用总预算**：`MAX_TOOL_CALLS = 24`。
3. **逐工具预算**：`TOOL_CALL_LIMITS` 表。比如 `check_conflicts` 只允许 1 次——查冲突本质上是一次性的事，模型反复查就是转圈信号。
4. **参数级重复检测**：`_call_key` 命中 `seen_calls` 直接拒绝，把"你已经问过了"这个信息回传给模型。

**关键设计**：所有限制**不是硬杀进程，而是回传结构化错误给 LLM**，让它自己纠正。模型看到"同一工具参数已经执行过，请根据已有结果直接作答"，通常下一轮就会收敛。实在收敛不了才由预算兜底。

**追问**：
- *"有没有出现过防不住的死循环？"* —— 有一种：模型在**不同参数**之间反复横跳（比如 A 方案不行试 B，B 不行试 C，A 又改了个时间……）。参数级去重拦不住。这个我靠工具级预算兜底，比如 `generate_plan` 限 2 次，第三次就被拒。
- *"为什么不用 Agent 框架（LangChain / LlamaIndex）？"* —— 想过，最终没上，原因有三：一是这个项目需要精确控制循环的每一步（预算、确认合并、Observation 压缩），框架的抽象反而挡路；二是框架的依赖和我的"只依赖 6 个库"冲突；三是自己写一遍才真正理解 Tool Calling 协议是怎么运转的，面试时我能从字节流讲起。我理解框架的价值在于快速搭原型，不在于生产系统的可控性。

#### Q8. 模型挂了怎么办？降级后还剩多少能力？

**答**（`app/llm/exceptions.py` + `loop.py` 的 `LLMStatus`）：

**第一步是分类，不是统一重试**。三种错误走三条完全不同的路：

| 错误 | 触发条件 | 处理 | 恢复性 |
|---|---|---|---|
| `LLMAuthError` | HTTP 401/403 | `fallback_until = inf`，**永久禁用真模型**直到进程重启 | 不自愈（配置错了，重试没意义） |
| `LLMRateLimitError` | HTTP 429 | 指数退避 | 会自愈 |
| `LLMTransientError` | 5xx / 超时 / 网络错误 | 指数退避 | 会自愈 |

**为什么要把鉴权失败单独拎出来？** 因为它是最常见的"永久性"故障。如果 Key 失效还按退避重试，等于持续骚扰上游还烧钱。直接置 `inf`，一次都不再试，只等用户改配置后点"重连"。

**退避算法**：
```
delay = min(60 × 2^(连续失败次数-1), 600)   # 60s → 120 → 240 → 480 → 600(封顶)
实际等待 = delay + random(0, delay × 0.2)     # 20% 抖动
```
抖动是为了**避免多个客户端在同一时刻集体重试**（惊群）。封顶 600s 是因为再长也没有意义——上游限流通常按分钟级恢复。

**降级路径**：真模型失败时，同一轮请求内切到 `MockProvider`（本地规则模式），基于关键词匹配（"删除"、"冲突"、"调整"、"撤销"）产出工具调用，继续走完这次对话。

**降级后还剩多少能力？** 我要说实话：**不是 100%**。
- ✅ 仍然可用：任务/事件/日程的查询、删除类意图、冲突检查、撤销、重排等**关键词明确**的操作，因为 MockProvider 靠关键词就能判断意图。
- ⚠️ 降级：需要语义理解才能判断意图的请求，比如"帮我把下周那堆事挪一挪别太密"——关键词匹配可能命中不准。
- ❌ 不可用：开放式创作，比如"根据我的任务帮我写个学习计划"。

所以简历上"降级后核心规划流程 100% 可用"这句话我更愿意表述为：**"降级后查询类与关键词明确的操作类意图仍可完成"**。规划引擎本身从来不依赖模型，所以**排期能力是 100% 在线的**——只是"决定排什么"的自然语言理解在降级。

**追问**：
- *"为什么鉴权失败不自动重试？"* —— 见上。但我也提供了 `/api/agent/reconnect` 端点，用户改完配置点一下就恢复，不需要重启进程。
- *"有没有测过降级路径？"* —— 有。`tests/test_llm_provider.py` 测了异常分类和代理回退，`test_agent_loop.py` 测了退避算法和状态机，还有 220 个用例里有一组专门覆盖"模型鉴权失败后走本地模式"的路径。
- *"环境代理挂了怎么办？"* —— 这个是实际踩过的坑。某些启动环境会注入失效代理，导致所有 LLM 请求失败。`openai_compat.py` 里做了：先正常走，如果报 URLError 且环境里确实有代理变量，就用 `ProxyHandler({})` 强制直连再试一次。既不破坏正常代理环境，又避免因为一个坏代理让模型永久降级。

#### Q9. 多步操作用户确认了，但中间失败了怎么办？

**答**（`app/agent/transaction.py` + `agent.py` 的 `_handle_confirmation`）：

确认流会**批量执行**多个工具（比如"删这 3 个事件"）。如果第 1 个成功、第 2 个失败，结果是"删了一半"，这在日程场景是不可接受的——用户会看到一个自己没预期的状态。

所以做了**补偿式事务**：
1. 执行前 `AgentDatabaseSnapshot.capture(db)`，把 6 张表（Task / Event / TaskDependency / Schedule / UserPreference / PlanVersion）的全部行序列化到内存
2. 逐个执行工具，任何一个失败就 `break`
3. 失败时 `snapshot.restore(db)`：`rollback()` 丢弃未提交改动 → 按 `_DELETE_ORDER`（子表在前）全删 → `expunge_all()` 断身份映射 → 按 `_RESTORE_ORDER`（父表在前）重建 → `commit()` → `expire_all()`

**这里有个很关键的隐性约束**：**执行期间被调用的工具不能自己 `db.commit()`**。因为快照只能复原当前 Session 范围内的状态，如果某个工具提前 commit 了，真实数据库已经动了，`rollback` 和重建都救不回来。

这个约束以前只存在于 commit message 里，后来我发现新人改工具时很容易踩，所以我把它写进了 `transaction.py` 的模块 docstring，还在 `_handle_confirmation` 上加了醒目注释，并加了 `ToolCommitNotAllowedError` 作为未来的硬约束预留。同时用测试把这个契约固定下来（`_MODELS` 与 `_DELETE_ORDER` / `_RESTORE_ORDER` 集合必须一致、顺序关系必须成立）。

**追问**：
- *"全表删了重建会不会丢数据？"* —— 只在这 6 张表范围内。而且这是**补偿**不是**事务**：真正的做法应该是让所有工具在一个事务里执行、靠数据库回滚。我选补偿是因为工具层普遍用 `db.commit()`（每个 service 方法自己 commit），改成统一事务要动所有 service，改动面太大。补偿方案在单用户本地场景下够用，代价是恢复后自增 ID 不保证连续，以及 restore 后旧的 ORM 引用会 `DetachedInstanceError`——这两个我都在 docstring 里写明了。
- *"为什么不用嵌套事务 / SAVEPOINT？"* —— SQLAlchemy 的 `Session.begin_nested()` 依赖 SAVEPOINT，SQLite 默认不开，而且工具层自己 commit 会让 SAVEPOINT 失效。补偿方案虽然"土"，但和现有 service 层的 commit 习惯兼容。
- *"这个方案你觉得哪里最弱？"* —— 工具自己 commit 那一条。这是架构级的问题，我目前的解法是"文档 + 注释 + 测试固定契约"，属于"用纪律换不改架构"。如果重来，我会先把 service 层的 commit 收归到一个统一的 Unit of Work。

#### Q10. 并发安全怎么做的？

**答**（这里可以讲我们实际修的 bug）：

FastAPI 的同步 endpoint 跑在 Starlette 的 anyio 线程池里，多个请求会**同时落到同一个 Memory 实例**。原来的 `Memory` 是个裸 dict：

```python
history = self._sessions.setdefault(session_id, [])  # 读 dict
history.append(message)                              # 改 list
if len(history) > 100:
    del history[:-100]                               # 又改 list
```

另一个线程同时走 `recent()` 迭代同一个 list，就会 `RuntimeError: dictionary changed size during iteration`。更隐蔽的是：即使不抛错，裁剪位置也可能跳，导致历史错乱。

修法是给 `Memory` 加一把 `threading.Lock`，所有对 `_sessions` 的读写都在 `with self._lock` 里。我还写了 8 个专门的测试：5 个顺序场景（保证加锁没破坏原行为）+ 3 个并发场景（Barrier 同步 16 线程同时跳 add/recent/replace，断言不抛异常、长度不越界、clear/hydrate 与 add 互斥不报错）。

**这个 bug 的发现过程也值得讲**：我第一版代码审查列了 18 个问题，但当时没有验证。等真正要修的时候，我先做了一轮 `git for-each-ref` + `git rev-parse --verify` 交叉验证，发现自己对分支状态的报告是错的（单次 `git branch -a` 输出不足以支撑结论）。之后我给自己立了规矩：**涉及删除/重置/推送的写操作前，必须先用只读命令交叉对账**。

### 3.5 规划引擎与 CP-SAT

#### Q11. 你的规划引擎具体怎么算的？

**答**（`app/planning/engine.py`）：

**第一步，算可用时间窗**（`windows.py`）：
- 从用户偏好拿工作时段（如 9:00–18:00）、午休（12:00–13:00）
- 扣掉周末开关、已存在的固定日程（Event）、已排的任务安排（Schedule）
- 每个窗口切成 15 分钟粒度的候选槽（`SLOT_MINUTES`）

**第二步，贪心排**（`generate_plan`）：
- 任务先按依赖做拓扑排序（`_dependency_order`），检测循环依赖
- 排序键 `_sort_key`：固定日程优先 → 按 `planning_weight` 降序 → 按截止时间
- `planning_weight` 按策略加权：`deadline_first` 优先看截止时间，`priority_first` 优先看优先级，`balanced` 兼顾
- 对每个任务，在窗口里找第一个不冲突的空槽，扣掉 gap（任务间隔）
- 长任务（`splittable`）按 `min_chunk_minutes` / `max_chunk_minutes` 拆段
- 排不下的进 `failures`，带上原因（"截止时间早于规划起始时间"、"前置任务尚未完成"）

**第三步，冲突检测**（`check_conflicts`）：区间重叠检测。
**第四步，计划质量评估**（`evaluate_plan`）：给分 + 列出未安排原因 + 逐项安排依据。

**追问**：
- *"贪心什么时候不够用？"* —— 当任务很多、约束复杂时，贪心可能因为"先排了一个占大块的任务"导致后面几个都排不下。CP-SAT 就是补这个洞的。
- *"怎么保证贪心和 CP-SAT 结果一致？"* —— 不保证，也不应该保证。它们是两条路径，CP-SAT 目标函数里显式加了 `duration_ticks * 20`（偏好把长任务排掉）和 `+180`（命中偏好时段加分）和 `- start_ticks // 8`（偏好早排）。贪心是"按序塞进去"，CP-SAT 是"全局找最优"，结果可能不同但都满足约束。UI 上会显示这次用了哪种引擎和为什么。

#### Q12. CP-SAT 那条路怎么建模的？（**这题最能体现深度，务必答细**）

**答**（`app/planning/optimizer.py`）：

**决策变量**：对每个任务、每个候选起始时刻，建一个 `BoolVar`（`task_{id}_{ticks}`），表示"这个任务放在这个时刻"。同时每个任务有一个 `scheduled_{id}` 汇总变量，表示"这个任务是否被排上"。

**区间建模**：用 `NewOptionalFixedSizeIntervalVar(start_tick, occupancy_ticks, choice, ...)`。占用长度 = 任务时长 + gap（任务间隔）。用 optional interval 而不是普通 interval，是因为任务可能不被排上。

**约束**：
1. `AddNoOverlap(intervals)` —— 所有区间互不重叠，这是硬约束
2. `sum(choice for 候选) == scheduled` —— 一个任务最多选一个时刻
3. 无候选的任务 `scheduled == 0` —— 强制不被排
4. 依赖约束：`scheduled[child] <= scheduled[parent]`（前置没排，后置也不能排）
5. 依赖的**时间序**约束：若 child 的候选开始早于 parent 的候选结束，则 `child_var + parent_var <= 1`（两者不能同时成立）

**目标函数**（`Maximize`）：
```
score = planning_weight(task, strategy, origin)   # 策略相关的基础分
      + duration_ticks * 20                        # 偏好把长任务排掉
      + 180 (若命中用户偏好时段)
      - (start_ticks // 8)                          # 偏好早排
```
最后一项是关键：它给了一个"早排"的梯度，使得求解器在同分方案里倾向更早的排期，但也通过系数大小（除以 8）保证不会压过策略权重。

**求解**：`max_time_in_seconds = 5`，`num_search_workers = 1`。

**一个有意思的工程细节**：CP-SAT 建模时我不知道某些"业务上非法但约束上合法"的组合（比如某个位置和另一个任务的地点路线不可达），所以我加了 `candidate_validator` 回调。求解后如果发现有非法分配，就把它加进 `banned` 集合、重新求解，最多循环 13 次。这是一种**求解 + 校验 + 迭代剪枝**的混合模式，因为这些业务约束不是线性的，没法直接写进 CP-SAT。

**追问**：
- *"为什么 time limit 是 5 秒？"* —— 这是个交互式产品，用户点"开始规划"后超过 5 秒就开始不耐烦了。5 秒能覆盖绝大多数规模（几十个任务、一周窗口）。超时后 CP-SAT 返回当前最好的可行解（FEASIBLE），不返回就返回失败降级到贪心。
- *"为什么不支持可拆分任务？"* —— 可拆分任务的建模需要引入"分段数"这一维变量和段间连续性约束，复杂度上一个台阶。当前显式 `raise RuntimeError("深度优化暂不支持可拆分任务")`，前端会提示用户。这种"明确不支持"比"跑出一个诡异结果"好。
- *"依赖约束怎么保证不会成环？"* —— 建模前先做拓扑排序，环检测在贪心路径里做（`test_task_dependencies_reject_cycles`）。CP-SAT 路径里依赖只用于收紧约束，成环的任务在 `eligible` 阶段就会被剔掉（前置不在 completed 也不在 pending 里 → 记 failure）。

#### Q13. 三种规划模式（自动/快速/深度优化）是怎么选和降级的？

**答**：
- **快速**：纯 Python 贪心，毫秒级，最少约束
- **深度优化**：CP-SAT，秒级，全局最优
- **自动**：按复杂度信号选——任务数量、时间跨度、是否有 splittable 任务、是否有依赖、是否有地点约束

**降级链是双向的**：
- 往上：CP-SAT 不可用（没装 ortools）→ 降级到贪心。`app/planning/optimizer.py` 顶部用 `try: from ortools.sat.python import cp_model / except ImportError: cp_model = None`，模块保持可导入，`is_cp_sat_available()` 给上层判断。这样"没装优化器"不会导致整个服务起不来。
- 往下：CP-SAT 超时 / 求解失败 → 同样降级到贪心

**关键**：降级原因会**显式返回给前端**（`engine_choice` / `degrade_reason` 字段），用户看到的是"因为任务数超过阈值，本次使用快速规则排期"，而不是一个说不清的结果。

**追问**：
- *"自动模式的选择依据是什么？"* —— 目前是启发式阈值（任务数、跨度天数）。可以更聪明，比如先跑一遍贪心看失败率，失败率高再上 CP-SAT。这是一个明确的优化点。

### 3.6 业务约束与外部集成

#### Q14. "时间不重叠但赶不及"怎么检测？

**答**（`app/services/travel_planning_service.py` 的 `TravelConstraintChecker.sequence_issues`）：

把日程拆成"块"（block），每块有起止时间、地点、是否 travel 段。相邻两块之间：
1. 出发时间 = `max(前一块结束, 后一块开始)`（travel 段的话，从后一块开始算）
2. 截止时间 = travel 段取后一块结束，否则取后一块开始
3. 可用时间 = 截止 - 出发
4. 需要的通勤时间 = 调用地图服务算的真实路线时长
5. 需要的 > 可用的 → 报冲突："固定行程冲突：从「马鞍山东站」前往「精沐精选酒店」需要约 41 分钟，按当前时间会迟到 21 分钟"

**两种模式**：
- 赶路段（`event_type="travel"`）：这段本身的时间窗就是通勤预算，用它的 `end_time` 当"最晚到达时间"，验证预留够不够
- 普通活动之间：直接查两点间的路线时间

**地图不可用时**（`MapNotConfiguredError`）：`_travel_minutes` 返回 `None`，检查跳过并记一条 warning "未配置高德地图，含地点安排尚未校验通勤时间"。**降级而不是假装没问题** —— 这一点我觉得很重要，宁可告诉用户"没校验"也不要假装通过。

**追问**：
- *"怎么避免误报？"* —— 有 `MAX_CONTINUOUS_GAP` 阈值，两个相隔很久的块不认为是连续的，不做路线校验。测试里专门有 `test_plan_analysis_ignores_unrelated_fixed_schedule_travel_conflict`。
- *"路线缓存吗？"* —— 缓存按 `(起点, 终点, 城市, 交通方式)` 四元组，TTL 24 小时，在 `MapService` 层统一做。

#### Q16. 怎么支持多家 LLM？

**答**（`app/llm/openai_compat.py`）：

**用标准库 `urllib` 直接调 `/chat/completions`，不引 SDK**。理由是所有主流服务都提供 OpenAI 兼容端点，兼容一个协议就兼容了全部：OpenAI、DeepSeek、通义千问、智谱、Kimi、Ollama、vLLM。

**这样做的好处**：
- 依赖只有 5 个，其中没有一个是 LLM SDK
- 换模型只改 `config.json` 里的 `base_url` / `model` / `api_key`，代码零改动
- Ollama / vLLM 本地部署也直接能用

**关键实现**：
- 错误按 HTTP 状态码分类：401/403 → `LLMAuthError`；429 → `LLMRateLimitError`；其它 → `LLMTransientError`
- 没有配 `base_url` 时 `from_config()` 返回 `None`，`build_agent()` 回落到 `MockProvider`，**整个系统仍然完全可用**（这是"本地优先"的含义之一）

**追问**：
- *"为什么不用官方 SDK？"* —— 官方 SDK 每家都不一样，要兼容就得写 7 个适配器；OpenAI 兼容协议是事实标准，写一个 urllib 调用就够。代价是拿不到各家 SDK 的高级特性（比如流式、tool call 的流式增量），但我用 `MockProvider` + 自建 SSE 的方式绕开了流式需求。

### 3.7 后端与工程

#### Q17. 前后端怎么设计的？为什么前端不用框架？

**答**：
- **后端**：FastAPI + SQLAlchemy 2.0 + Pydantic v2 + SQLite。10 个 router，11 个 service，9 张表。
- **前端**：**原生 JS，零框架零构建**。`app.js` 3900 行 + `index.html` 900 行 + `style.css` 4100 行。直接 `<script src>` 引入，没有 npm、没有打包步骤，改完刷新就生效。

**为什么不用 Vue/React**：
1. **零构建**意味着没有 node_modules、没有 lockfile 冲突、没有"npm install 挂了项目就跑不起来"的问题
2. 这个项目的交互复杂度不高——主要是表格 + 时间轴 + 一个 7×24 网格。React 的价值在复杂状态管理，这里状态就是一个普通对象（`state`），十几行就能管住
3. 打包产物要提交进仓库的话，diff 会变得很难读

**代价我也认**：`app.js` 3900 行单文件，函数多了以后维护性下降。再做两个页面就该拆模块了。真实项目我会考虑用 Vite + 原生 ES Module（保留零框架，只加构建）或直接上 Vue。

**追问**：
- *"前端怎么跟后端通信？"* —— 一个 `api()` 包装函数统一处理 base URL（自动从 `window.location` 推 `host:8000/api`，所以换 IP 访问不用改代码）、JSON 序列化、错误弹窗。
- *"SQLite 够用吗？"* —— 单用户本地工具够用，而且 SQLite 免安装、免配置、事务可靠。多人场景要换 PostgreSQL。

#### Q18. 时间怎么处理的？（这是个高频陷阱题）

**答**：
- **存储**：数据库里**统一存不带时区标记的 UTC**。`app/utils.py` 的 `utcnow()` 统一给 naive UTC。
- **传输**：API 出口统一带 `Z` 后缀的 ISO 8601。
- **显示**：界面按用户偏好里的 `timezone` 转成本地时间。
- **规划**：引擎内部全部用 UTC 算。

**为什么这么设计**：时区转换是最容易出 bug 的地方，尤其是夏令时。如果库里存本地时间，跨时区访问、夏令时切换、用户改时区偏好，全都会出问题。统一 UTC + 显示层转换是唯一能长期维护的做法。

**prompt 里也写死了这条规则**（system prompt 的"时区规则"段）：告诉模型"用户在 UTC+8 说下午 2 点，应该传 06:00Z"。模型不擅长时区转换，与其指望它算对，不如在 prompt 里给明确的换算规则和例子。

**追问**：
- *"用户改时区偏好怎么办？"* —— 存量数据不变（还是 UTC），只是显示变了。已有排期的时间点不会平移——因为它们本来就是绝对时刻。这是对的：用户在纽约出差，把时区改成 America/New_York，日程的绝对时刻不应该变。

#### Q19. 数据库表怎么设计的？

**答**（9 张表）：

核心的三张：
- `tasks` —— 待办任务。有 `estimated_duration` / `splittable` / `min_chunk_minutes` / `max_chunk_minutes` / `dependency_ids` / `location_id` / `priority` / `deadline`
- `events` —— 固定日程（外部不可移动的约束）。有 `event_type`（activity / travel）/ `travel_mode` / `origin_location_id` / `trip_id` / `trip_order`
- `schedules` —— 任务安排（规划器为 Task 生成的可调时间块）。有 `task_id` / `chunk_index` / `status`（proposed / accepted）/ `is_locked` / `plan_batch_id`

**统一日程表达**是这个项目的核心抽象：
- `Event` = 外部时间已确定、不可移动 → 规划器必须绕开
- `Schedule` = 系统为 `Task` 生成的时间块 → 可调整、可锁定、可撤销
- `Task` = 尚未确定具体时刻、可由规划器移动

**其他表**：`user_preferences`（长期偏好）、`locations`（常用地点，带经纬度）、`plan_versions`（计划版本快照，用于撤销）、`pending_actions`（待确认操作，跨进程持久化）、`chat_messages`（对话历史）、`agent_runs`（执行轨迹）、`evaluation_runs`（评测结果）。

**追问**：
- *"为什么 `Schedule` 要单独建表而不是在 Task 上加个时间字段？"* —— 因为一个任务可以有多段（splittable），而且同一批规划的结果要能整体确认/整体撤销。独立表才能表达"多段"和"批次"。
- *"`plan_versions` 怎么用？"* —— 每次修改前把当前状态快照存一份，同时记结构化 diff（保留/移动/新增/移除/不变）。`undo_latest_plan` 读最近一版做逆向操作。

### 3.8 测试与评测

#### Q20. 你怎么测一个 Agent？

**答**：**普通单测测不了 Agent**，因为输出不确定。所以我分三层：

**第一层：确定性单测（220 个）** —— 测的是"确定性部分"：
- 规划引擎的优先级、间隔、过去时间保护、午休避让、依赖拓扑、任务拆分（`test_planning_engine.py`）
- Service 层的锁定、局部重排、版本撤销、冲突检测（`test_services.py`）
- Agent Loop 的状态机、退避算法、异常分类、工具预算（`test_agent_loop.py`）
- 用 `MockProvider` 脚本化 LLM 输出，让 Agent 的行为完全确定

**关键手法**：用 `MockProvider(script=[...])` 预设模型每一轮返回什么，Agent 的执行路径就完全可复现了。

**第二层：端到端评测（5 个场景）** —— `app/services/evaluation_service.py`：
- 场景：紧急任务自动规划 / 旅行行程整组创建 / 旅行行程整体顺延 / 相关事件批量删除 / 冲突查询
- 每个场景声明 `expected_tools`（必须调用）、`forbidden_tools`（禁止调用）、`expects_confirmation`（是否该要确认）
- 五个指标：
  - `tool_selection_accuracy` —— 工具选对率（权重 0.35）
  - `tool_success_rate` —— 工具成功率（0.25）
  - `constraint_pass_rate` —— 约束通过率（0.25）
  - `confirmation_safety_rate` —— 确认安全性（0.15）
  - 加上 `average_latency_ms` / `total_model_tokens` / `estimated_model_cost`
- 加权总分 = 0.35×选择 + 0.25×成功 + 0.25×约束 + 0.15×确认

**第三层：可观测轨迹** —— `agent_runs` 表持久化每一步：请求识别、工具预览/执行、确认、复查、状态、耗时。前端可回看。

**追问**：
- *"为什么工具选择正确率权重最高？"* —— 因为工具选错是 Agent 失败的第一大来源，后面全错位。选对工具是 80% 的工作量。
- *"确认安全性怎么算？"* —— 场景声明了 `expects_confirmation`，实际 Agent 的 `confirmation.required` 和它一致才算通过。比如"批量删除"场景必须要求确认，如果模型直接删了就是安全失败——这测的是"Agent 会不会在危险操作上擅自做主"。
- *"评测用真模型吗？"* —— 评测框架跑在**隔离的临时数据库**上，避免污染真实数据。模型可以用真的也可以用 Mock。

#### Q21. 你怎么保证代码质量？

**答**：
1. **测试先行**：每个功能配对应测试，220 个用例覆盖规划优先级、冲突避让、过去时间保护、时区换算、依赖拓扑、任务拆分、日程组原子性、确认流回滚、并发安全
2. **契约测试**：像 `AgentDatabaseSnapshot` 的 `_MODELS` / `_DELETE_ORDER` / `_RESTORE_ORDER` 集合一致性和顺序关系，我是写测试固定住的——防止有人改了常量但忘了改顺序，restore 时 FK 直接报错
3. **纯函数优先**：规划引擎不碰 I/O，所以能写非常细的断言（"这个任务必须在第 2 天上午"而不是"结果里应该有它"）
4. **每次修复都补回归测试**：比如我修并发 bug 时补了 3 个并发测试（Barrier 同步 16 线程），修事务契约时补了 9 个

**追问**：
- *"覆盖率多少？"* —— 我没有测覆盖率工具（不想加依赖），靠的是"每个公开函数至少一个测试"+ 上面那些契约测试。但我知道这是短板，测的是"行为对不对"，不一定是"每行都跑到了"。

### 3.9 其它可能问的

#### Q22. 技能段说"熟悉 ReAct"，你的实现是 ReAct 吗？（**这题必须诚实回答**）

**答**（诚实版很重要）：

严格说**不是经典 ReAct**。经典 ReAct 是显式的 `Thought → Action → Observation` 文本循环，每一步都把推理写出来。我实现的是 **function-calling loop**：模型通过 `tool_calls` 字段表达动作，推理过程在服务端（`reasoning_content` 字段我原样透传保留了）。

**相同的地方**：多步、工具执行、结果回传、基于观察继续决策——这个骨架是一致的。
**不同的地方**：没有显式的 Thought 文本，没有"写下来思考"这个约束。

**为什么这么实现**：function-calling 协议下，模型的结构化输出更稳定、参数更可靠，解析成本也低。而且我保留了 `raw_message` 里的 `reasoning_content`，需要看推理链时能拿到。

**如果要做显式 CoT**，我的思路是：在 `system_hint` 里加"先输出简短推理再调用工具"，但要评估延迟和 token 成本上升，以及推理文本里可能泄露的信息。

**这个区分很关键** —— 面试时说"我实现的是 function-calling loop，保留了 reasoning_content，和 ReAct 同构但不是标准形态"，比硬说是 ReAct 强得多，因为面试官追问三层你就会露馅。

#### Q23. "Context Memory 管理"具体是什么？

**答**：
我的实现分四层：
- **短期**：`Memory` 类，进程内的会话历史，按 session 隔离，最多保留 100 条，超了从头裁剪。
- **发给模型的上下文**：按 token 分三档管。单条超 1200 token 先压缩；整段历史预算 3600 token，从最新往回累加、超了丢最老的，并在 system prompt 里注明"最早 N 条已省略"；整包预算 18000 token，超了按体积从大到小降级工具结果——剥掉 data 只留 success / summary，`tool_call_id` 和 name 不动，因为协议要求每个调用都有对应的 tool 消息，所以只瘦身不删除。
- **长期**：`user_preferences` 表，存工作时段、午休、任务间隔、规划策略、默认地点、时区。
- **持久化**：`chat_messages` 存对话文本、`agent_runs` 存执行轨迹、`pending_actions` 存待确认操作。

**为什么历史要二次裁剪**：上下文预算是共享的，system prompt 和工具 schema 先占掉一大块，剩下才是历史。如果不裁，一个用了两周的会话会把可用空间吃光。但我不会去说"system prompt 占 1500 token"这种数——没有按目标模型的分词器算过，说出来就是编的。

**压缩策略是"按信息密度打分"，不是头尾截断**：每段按约束词（必须 / 截止 / 锁定 / 之前）+3、时间 +2、ID 与数字 +1、过长过短降权打一个分，首尾两段恒定保留，中间按分数贪心填充；组装完复核总量，超了丢掉分数最低的段再重排。为什么不用头尾截断？因为它会把刚保住的关键句拦腰切断——这个 bug 是我写测试时抓到的。

**追问**：
- *"会不会把约束丢掉？"* —— 会，但方向和以前相反。以前头尾各截一刀，丢的是中间且不可控；现在约束句打分最高，优先活下来的是它，先被丢的是纯叙述。救不回来的是"从没进过这 10 条窗口的早期事实"，那需要摘要层，当前没做。
- *"会话历史丢了怎么办？"* —— 内存态，服务重启就没了。但 `chat_messages` 表持久化了对话，`agent_chat` 入口会 hydrate 回内存。所以重启后同一个 session_id 能恢复。
- *"那为什么还要放内存？"* —— 热路径不该每次查库，而且裁剪逻辑需要频繁做。

#### Q24. 怎么防止用户误删数据？

**答**（分层）：
1. **确认等级**：`delete_events` / `delete_task` 是 `confirm` 级，Agent 只能发起"待确认"，真正执行要用户点确认
2. **批量合并**：删 5 个事件只要点一次确认（预览里能看到全部 5 个）
3. **版本快照 + 撤销**：每次修改前存快照，`undo_latest_plan` 一键撤销
4. **行程组原子性**：旅行行程的删除是整组的，不会留下半段
5. **执行后审计**：执行完再跑一次冲突检查，发现问题自动回滚并告知用户

**追问**：
- *"确认请求会过期吗？"* —— 10 分钟 TTL。`PendingActionStore` 现在落库到 `pending_actions` 表，所以多 worker（不同请求落到不同进程）都能看到同一份待确认集，服务重启也不丢。

## §5 行为面试题（STAR 准备）

### Q26. 讲一个你遇到的最大技术难题。

**选材**：**跨分支合并时把远端一个坏 commit 合进来，导致整个测试套件红**。

- **S**：要把本地 12 个提交推到远端，但远端 `origin/improvement` 不知道什么时候多了一个提交，两边分叉了。
- **T**：既要保住远端那个提交，又不能让本地的成果丢掉。
- **A**：先做只读对账（`git for-each-ref` + `git rev-parse --verify`），画出提交图，发现两边从共同祖先 `1e84999` 分了叉。而且进一步发现**远端那个 commit 本身是坏的**——它删掉了 `app/api/agent.py` 的 `import time` 但保留了 `time.perf_counter()` 调用，还调用了一个没定义的方法 `_read_response`。
- **R**：先 `git reset --hard` 回退到合并前，然后用 `-X ours` 重新合并保留本地版本；然后补回 `import time`（单独一个 commit）。之后跑全量测试，从 106 个用例里揪出另一个"时间敏感的测试"（硬编码了已经过去的日期 + mock 范围没盖到确认阶段）。最后 220 个用例全绿。

**这个故事的额外价值**：它引出我给自己立的规矩 —— **涉及删除/重置/推送的写操作前，必须先用只读命令交叉对账**。因为我自己就犯过这个错：第一次只看单次 `git branch -a` 输出就下结论说有几个分支、哪些是重复的，重新核查后发现结论是错的。

### Q27. 你怎么保证代码不被后来人改坏？

**答**（三个层次）：
1. **测试**：220 个用例，尤其是契约测试（表顺序集合必须一致这种）
2. **文档即约束**：`transaction.py` 把"工具不得自己 commit"写在模块 docstring 里，`_handle_confirmation` 上加显眼注释。改代码的人先读 docstring 就能知道契约
3. **可观测**：执行轨迹持久化，线上出问题能定位到具体是哪一步

**举实例**：我把"工具不得 commit"这个隐性约定从"只在 commit message 里"变成"docstring + 注释 + 测试"三处冗余，就是因为这类约定最容易在重构时丢。

### Q28. 遇到和 AI 意见不一致怎么办？

**答**（用这个项目的真实例子）：
项目里"自定义"和"今日"两个范围按钮，我一开始觉得该保留，是"用户可能需要"。后来实际用起来发现：

## §7 行业视野题（Agent 方向热点）

**准备观点，不要背结论。**

### Q29. 现在 Agent 的主要瓶颈在哪？

**我的看法**（三层）：
1. **评测**：最大的瓶颈。现在 Agent 的"好不好"还是靠人看 demo。缺的是**可复现的端到端指标**。我项目里的评测页是往这个方向走的粗糙版本——5 个场景、5 个指标，但场景数太少、指标还是设计出来的而非统计出来的。
2. **上下文工程**：不是"上下文窗口不够大"的问题，是"塞什么、塞多少、怎么压缩"的问题。工具结果可能几百 KB，塞进去就是噪声。我的实践是按结构裁剪（深度/条数/字符数三级限制）+ 保留决策相关信息。
3. **失败模式**：Agent 的失败往往不是"做错一步"，而是"做错了一串但没人发现"。所以我更关注**执行轨迹 + 审计 + 回滚**，而不是让模型更聪明。

### Q30. MCP（Model Context Protocol）你了解吗？你的项目能用上吗？

**答**：
了解。MCP 是把工具/资源用统一协议暴露给模型的标准，解决的是"每个应用的工具接入都要自己写一遍"的问题。

**我的项目能用上吗？** 可以，但收益有限——我的 37 个工具是**自己进程内的 Python 函数**，调用零网络开销、零序列化。套 MCP 会引入 JSON-RPC 往返和进程边界，反而更慢。

**真正适合 MCP 的场景**：工具在另一个进程/服务里（比如公司的内部 API、数据库查询服务），需要标准化接入。我的架构里 `app/integrations/` 这一层（地图、天气、未来的第三方业务系统）是最自然的 MCP 接入点——把外部服务包装成 MCP Server，本地 Agent 通过 MCP Client 调。

**这个回答的价值**：说明我知道 MCP 的价值边界，不是无脑跟风。

### Q31. RAG 和你的项目什么关系？

**答**：**目前没有关系，我也没硬加。**

日程排期需要的上下文是"当前有哪些任务、哪些事件、用户偏好"——这是**结构化查询**，直接查数据库比做 embedding 检索更准更快。RAG 适合的是"知识在非结构化文档里"（比如"公司的报销制度写在 wiki 里"）。

**如果要做**：比如把用户的邮件、微信消息导入，让 Agent 从里面提取出待办任务——那确实是 RAG + LLM extraction 的场景。技术上我会：
1. 切分 + embedding
2. 检索 top-k
3. 让 LLM 从检索结果里抽取结构化任务（标题、时长、截止、依赖）
4. 抽取结果进 `tasks` 表，走现有的确认流程

**但要小心**：抽取的准确率决定后续一切，所以必须有人工确认环节。这也是我现有 `confirm` 级工具设计的原因。

### Q32. 多智能体你怎么看？

**答**：我的判断是**大多数多智能体系统是过度设计**。分工的理论收益是真的（不同角色有不同的 prompt 和工具集），但代价是：
- 通信开销和延迟叠加
- 错误会在智能体之间传播且难以定位
- 调试难度指数级上升

**我的项目里"多智能体"的影子是 Skill 路由**，但它不是独立 Agent，是"同一次调用里切换 prompt + 工具白名单"，没有跨 Agent 通信。

**什么时候真需要多智能体**：任务能真正并行且子任务间弱耦合（比如"同时调研 5 个竞品"）。日程排期是强依赖的串行任务，拆多智能体没有收益。

### Q33. 如果让你重做这个项目，你会怎么改？

**答**（这题一定要答，且要真诚）：

1. **先做评测再做功能**。我是反过来的——先堆功能，后补评测。结果是评测框架建立时，很多设计已经固化了，评测指标只能挑"我设计得出来的"而不是"我真正关心的"。
2. **统一事务边界**。现在的补偿式事务是"用纪律换不改架构"。应该一开始就把 service 层的 `commit()` 收归到一个 Unit of Work，工具层只声明"我要改什么"。
3. **更早引入真实用户**。哪怕 3 个人用，也比 0 个人用强。我直到很后期才发现"自定义"按钮是死代码。
4. **前端拆分**。`app.js` 3900 行单文件是技术债，应该按模块拆。

**但我也要说清楚为什么这么选**：这个项目的核心假设是"LLM 不擅长算时间"——这个假设必须最先验证，如果验证不成立，整个架构就不成立。所以我先做核心引擎和工具层，再回头做评测和体验。**如果重来我会先花一周做一个"LLM 直接排期 vs 确定性引擎"的 A/B，用数据证明解耦的必要性**，再投入后面的工作。

## §8 压力题 / 陷阱题

### Q34. 这个项目是不是就是调 API？

**答**：不是。调 API 部分占代码量的一小块。核心复杂度在三处：
1. **不可靠的依赖如何隔离**（模型会错、会限流、会挂）
2. **副作用如何安全执行**（多步操作、删除、确认、回滚）
3. **时间与约束的正确性**（时区、依赖、通勤、午休、间隔）

一个"调 API"的 demo 我两天就能写完。写成一个**敢在真实数据上执行删除操作**的系统，是完全不同的工程量。

### Q35. 你怎么知道你的系统是对的？（除了测试）

**答**：三层：
1. **不变量测试**（invariant-based）：比如"任意排期结果内不能有区间重叠"、"任务不能排在截止时间之后"、"依赖任务必须在前置之后"。这些用 property-based 思路写。
2. **黄金用例**：把人工排过的方案存成基线，回归时对比。
3. **端到端评测**：5 个场景 × 5 指标。

**我承认的不足**：目前主要靠"写死期望值"的断言，property-based 我只做了一部分（依赖环检测、过去时间保护）。

### Q36. 如果我说你的系统有 bug，你怎么办？

**答**（这题考的是态度）：
1. **先复现**，用我项目的调试手段（执行轨迹 + 持久化的 Run 记录能定位到具体哪一步）
2. **写一个失败的测试**固定住
3. **修**，让测试变绿
4. **跑全量**确认没有回归
5. **提交信息里写清根因和修法**

**我自己的例子**：合并远端分支时，`import time` 被吃掉导致所有 `/api/agent` 测试报 `NameError`。我是先看测试报错定位到具体行，再查 git 历史发现是远端 commit 自带的 bug，最后分两个 commit 修（一个补 import，一个修测试的 mock 范围）。

### Q37. 你最近在看什么技术？

**答**（准备 2–3 个真的看过的，不要泛泛而谈）：
- **上下文工程**：具体看的是 Anthropic 那篇 context engineering 的文章和长上下文的"中间遗忘"现象
- **Agent 评测**：看的是轨迹评测（trajectory evaluation）vs 结果评测（outcome evaluation）的取舍
- **结构化输出**：JSON Schema 约束解码 / constrained decoding，看它比"prompt 里要求输出 JSON"稳定多少

**诚实原则**：说"最近在看"就真的看过，问细节能答上来。答不上来就说"了解概念但没深入用过"。
