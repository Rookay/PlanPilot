# 使用说明

这份定稿把此前三份材料（开口稿、速记页、120 题字典）合并成一份，只做三件事：按技术领域归类、按被问概率排序、每题给出“能直接说的答案”和“被追问时才给的边界”。

**概率标记。** 标题后的 A / B / C 表示面试中出现的可能性，不是重要性。

| 标记 | 含义 | 要求 |
| --- | --- | --- |
| A 必问 | 几乎每场都会出现，或说不清就会被打断 | 脱稿，30～60 秒讲完，不能卡 |
| B 高频 | 顺着项目细节必然会追到 | 能讲 30 秒，不主动抛 |
| C 备查 | 特定面试官或特定方向才会问 | 知道结论和位置，被问到再展开 |

**回答节奏。** 结论 → 机制 → 一个具体例子。**边界留给追问，不要写进开场白。** 大多数候选人失分不是因为不会，而是一开口就把所有限制说完，听起来像没做完。

**时间盒。** 只剩两小时，只看附录 H 列的 21 道核心题；有半天，把标 A 的全部过一遍再加 B；有两天，全过并做一次 45 分钟模拟。附录 H 有对应的复习顺序。

# 第一部分 项目定位与整体架构

## 1.1 一分钟介绍项目（A 必问）

**15 秒版。** 我独立做了一个本地优先的日程规划 Agent：LLM 负责理解需求和选工具，本地规划器负责算时间，中间用确认和补偿兜住写操作。

**完整回答。**

> PlanPilot 是一个本地优先的智能日程规划 Agent。用户可以用自然语言提“优先安排论文、避开组会、任务之间留半小时”这类要求。我把系统分成两层：LLM 负责理解需求和多步工具决策，本地规划器负责时间窗口、截止时间、依赖和通勤这些确定性约束。
>
> Agent 层是 ReAct 风格的循环，动作由原生 Function Calling 表达：模型返回工具调用就执行，把结构化结果作为 Observation 回传，再进下一轮。注册了 37 个工具和 10 个场景 Skill，配了上下文裁剪、调用预算、危险操作确认和模型故障降级。业务侧有 CP-SAT 全局优化、局部重排和计划撤销。目前 236 个测试方法、5 个确定性评测场景和持久化执行轨迹。
>
> 一句话概括：模型负责软决策，工具和业务代码负责硬约束，两者之间用 Agent Runtime 管住调用、确认、失败恢复和验证。

**最可能被接着问的三件事。** 你自己做了哪部分（全部，从数据模型到前端确认）；最难的地方（多步写操作部分成功，见 6.2）；挑一条链路讲代码（查任务 → 改优先级 → 生成带间隔的计划）。

## 1.2 项目的规模和完成度怎么说（A 必问）

> 当前是个人项目，规模指标体现的是实现范围，不是线上效果。可以确认的静态事实是：37 个注册工具、10 个 Skill、236 个测试方法、5 个基于 Mock 的端到端评测场景、11 张 ORM 表、9 个 APIRouter、6 项直接运行依赖。
>
> 效果证据是核心路径测试、确定性场景回归和可追溯的执行记录。我没有真实用户统计，所以不会把测试数量说成线上成功率。

**边界。** 测试数量不等于覆盖率；5 个场景用的是 Mock，不代表真实模型的理解准确率。这两个口径必须自己先说清楚，否则后面每句话都会被怀疑。

## 1.3 为什么做这个项目（A 必问）

> 我想做的不是一个能聊天的助手，而是一个能把模型输出接进有约束的业务系统的 Agent。日程规划刚好同时具备三种难点：自然语言有歧义、时间约束必须算准、写操作失败会留下中间状态。它能把 Agent 工程里最难的部分都逼出来。

**追问“市面上不是有很多日程工具吗”。** 不要贬低竞品。答：现成产品的价值在日程管理，我的价值在把“理解—决策—执行—验证”整条链路自己实现一遍，并且能解释每一步的失败边界。

## 1.4 “本地优先”到底指什么（A 必问，防守题）

默认配置里 LLM 走远端 API。说“本地优先”而不解释，面试官一句“任务内容不还是发给云端了”就能问住。

> 本地优先指三件事：数据落在本地 SQLite；排期计算完全不依赖模型；模型层可以整体换成本地 Ollama 或 vLLM。默认配云模型只是部署选择——本地模型质量不够，但架构上随时能切回完全离线。
>
> `app/llm/` 是抽象层，`openai_compat` 只是其中一个实现，base_url 指向 Ollama 就能跑。换 provider 只改配置，不动业务代码。

**边界。** 地图和天气是外部依赖，断网时不可用；“本地优先”不等于“全功能离线”。

## 1.5 整体架构怎么分层（A 必问）

> 四层。最上面是原生 HTML/CSS/JS 前端；中间是 FastAPI，分普通业务路由和 Agent 对话路由；再往下是 Agent 层，包含门面、循环、Skill、工具注册表和 LLM Provider；最底下是 Service、规划引擎、SQLAlchemy 和 SQLite。
>
> 关键点是 Agent 不是所有 Service 的上层。前端可以直接调 Service，Agent 则通过 Tool 复用同一套业务能力，两条入口共用一套规则。

**一句话画图。**

前端 → API →（普通路由 → Service）／（Agent 路由 → Loop → Tool → Service）→ 规划引擎／数据库

**追问“为什么不让 Agent 直连 Service”。** Service 是给程序调的，没有模型需要的工具说明、参数 schema 和确认等级。Tool 补齐这些信息，Registry 统一管理入口。

## 1.6 一次请求的完整链路（A 必问）

> 请求先过 Pydantic 校验，生成或复用 session_id；内存里没有这个会话就从 chat_messages 恢复用户和助手文本。门面区分普通消息和确认请求：普通消息进 Loop，确认请求进确认分支。
>
> Loop 里先做一次关键词先验，命中高置信业务词就带入对应场景策略，没命中走通用模式；然后组织 system prompt、世界状态摘要和最近历史，把过滤后的工具 schema 发给模型——按场景白名单收窄、剔除额度耗尽的工具，但场景切换工具永远保留。模型认可当前场景就直接调业务工具，不认可就在第一轮用 `select_skill` 换掉。返回文本就结束；返回 tool_calls 就校验、预览或串行执行，把结果回传进下一轮。同一轮里所有 confirm 级调用先各自预览，再合并成一次确认落 pending_actions。
>
> 门面在返回前对已应用的变更做一次执行后审计，追加工作流步骤和告警；API 汇总状态、耗时、token 和估算成本，写 AgentRun 和对话文本，最后返回 JSON。

**边界。** 轨迹主要在一次 handle 返回后统一记录，进程中途崩溃不能保证每步都落盘。逐步事件落盘和可恢复执行是下一阶段的事。

## 1.7 为什么 API、Tool、Service 要分三层（B 高频）

> API 负责 HTTP 输入输出；Tool 负责给模型提供能力描述、参数入口、确认等级和可读结果；Service 负责可复用的业务规则和数据库操作。
>
> 这样“修改任务”这一个能力，前端按钮和 Agent 调用走的是同一段业务逻辑，不会随着时间分裂成两套规则。分层的目的不是好看，是让两个入口共享同一份正确性。

## 1.8 Agent 有哪几种状态（C 备查）

至少分清四层，不要混成一个枚举：会话上下文（`chat_messages` 历史与 `user_preferences` 偏好）、单次运行（局部变量与 AgentRun）、模型服务状态（进程内的 ok / rate_limited / auth_failed）、业务实体状态（Task 的 pending / completed，Schedule 的 proposed / accepted）。

**这一题的价值。** 能分层说明你理解“状态存在哪、重启后还剩什么”，而不是把所有东西都叫“上下文”。

# 第二部分 Agent 循环与推理

## 2.1 Agent Loop 到底怎么跑（A 必问）

> 每轮把当前上下文和可见工具 schema 发给模型。返回文本就结束；返回 tool_calls 就逐项检查工具是否存在、是否重复、是否超过单工具额度，再预览或执行，把结构化结果回传给模型。达到迭代或调用阈值后，转入无工具总结。

**循环结构。**

用户 → Skill 与上下文 → LLM → tool_calls → 校验与执行 → Observation → 下一轮 → 最终回答或等待确认

**具体例子。** 查论文任务 → 提高优先级 → 生成留 30 分钟间隔的计划 → 总结。

**追问“同轮多个工具并行吗”。** 当前串行处理。互不依赖的只读查询理论上可以并行，但并行要考虑 Session 不能被多个执行单元共享，收益要用 p95 延迟验证，不是想当然。

## 2.2 这是 ReAct 吗（A 必问）

> 是。我按 ReAct 的“推理—行动—观察”组织闭环，但动作由模型原生 Function Calling 表达，不是在文本里解析 Thought/Action/Observation。
>
> 区别在协议层：工具调用的格式由接口保证合法，我不需要写解析器，也不用处理“模型把 JSON 写坏了”这类问题，精力放在参数语义和业务校验上。

**被追问“那你有真正的思维链吗”。** 诚实答：文本 ReAct 会把推理显式写出来，Function Calling 模式下模型不一定输出完整思考链。所以准确说法是“ReAct 的组织方式 + Function Calling 的动作表达”，不宣称思维链可见或已持久化。

**术语层次。** ReAct 是组织思路，Function Calling 是动作机制，Agent Runtime 是调用与终止，Workflow 是确认与补偿这类固定流程。四层分开讲，比只点头清楚得多。

## 2.3 为什么把 LLM 和规划引擎分开（A 必问）

> 因为“理解用户要什么”和“算出具体排在哪”是两个问题。
>
> 用户说“论文优先、避开组会、任务之间留半小时”。LLM 负责把这句话拆成查任务、改优先级、调用规划工具并把间隔设成 30 分钟；规划引擎再根据时长、截止时间、已有日程和依赖，算出每个任务落在哪个时间段，排不下的返回原因。
>
> 好处是排期有明确规则、能独立测试、失败能定位；LLM 只负责把自然语言转成操作，并解释结果。

**记住这个例子。** LLM 把“论文优先、留出休息”转成工具调用；引擎算出“论文周二九点开始，下一个任务十点半开始”。

## 2.4 为什么自研 Loop，不用 LangGraph（A 必问）

> 项目初期评估过框架，最后没用的理由有三个：我需要在循环层精确控制迭代预算、逐工具额度、参数级去重和 Observation 压缩，框架的粗粒度开关不够拆；依赖体积会从 6 项涨到二十多项；自己写一遍才能真正理解 function calling 的失败模式。
>
> 但我也补了 LangGraph 的对照实验，它在显式状态管理和可中断恢复上比我做得好。所以我现在的判断是：核心链路自研，周边能力可以用框架；如果重来做 RAG，我会用 LlamaIndex，Agent 核心仍然自研。

**不要说。** “框架只适合 demo，不适合生产。”这是给自己挖坑，也会显得没做过对比。

## 2.5 什么时候用工作流，什么时候用 Agent（B 高频）

> 步骤明确、容错要求高的环节用工作流，比如确认、提交、审计；需要根据输入和反馈动态选动作的部分交给 Agent。
>
> PlanPilot 就是这个结构：工具选择是动态的，写入授权和业务校验是确定性的。外层工作流约束，局部 Agent 决策。

## 2.6 工具调用的历史会跨轮保存吗（B 高频）

必须分四种情况：本次 run 内，局部 messages 保存 tool_calls 和 tool 结果，供后续轮次使用；跨用户消息，表里只留用户和助手的对话文本，工具轨迹不带过去；重启恢复，从 `chat_messages` 读到的就是文本，不是执行到一半的 Agent；执行轨迹，AgentRun 用于回看，不等于能重放模型上下文。

**一句话。** 能恢复会话，不能恢复执行。

# 第三部分 工具系统

## 3.1 Tool Registry 怎么设计（A 必问）

> 每个工具继承统一基类，声明名称、描述、输入 schema、确认等级，实现 execute 和 preview，返回统一的 ToolResult。Registry 负责注册、查找、把 schema 整理成模型可读的 function 描述，并统一捕获普通异常转成失败结果。
>
> 工具内部不重复实现业务逻辑，而是调 Service。比如创建任务工具调用任务 Service，前端手动创建也调它，两个入口一套规则。

**结构。**

Tool：name / description / input_schema / confirmation / execute / preview

Registry：register / get / names / schemas / execute / preview

ToolResult：success / data / error / summary / needs_confirmation

**边界。** 发给模型的是 name、description 和 parameters；output_schema 虽然在基类声明，但没有统一下发，也没有执行输出校验。别把它说成完整的双向 schema 约束。

## 3.2 37 个工具怎么分类，粒度怎么取（B 高频）

场景理解 1 个、任务 6 个、固定事件与行程组 9 个、日程 5 个、规划与分析 9 个、偏好 2 个、时间与天气 2 个、地图 3 个。

> 读工具保持小粒度，便于组合；有强一致性要求的写操作封装成业务级工具。比如整组行程修订用 revise_trip，而不是让模型连续调多个 update_event——前者能整体校验时间线，也能控制部分失败。

**判断标准。** 这个操作是否天然构成一个业务意图，是否需要共同校验和共同提交。过细会让模型管理大量中间 ID，过粗会让参数爆炸、职责不清。

## 3.3 Skill 是什么，和多 Agent 有什么区别（B 高频）

> Tool 是可执行能力，Skill 是场景策略，包含关键词、优先级、场景提示和可选的工具白名单。比如旅行规划会引导模型先查地点和路线、再批量创建行程。
>
> 当前是一个 Agent 用不同 Skill，不是 10 个独立 Agent。

**两层路由。** 第一层是关键词先验：候选 Skill 至少命中一个关键词后，按（priority，命中关键词总长度，命中数量，注册顺序）排序，第一项胜出。第一比较项是优先级，不是命中数量。

**第二层是模型自选。** 关键词没命中、或者命中了但不是真实意图时，模型可以调 `select_skill` 按 name 覆盖当前场景，覆盖后不再走关键词匹配。切换次数单独限 3 次，且不计入 24 次业务调用预算。关键词先验负责省一次决策，模型自选负责兜底和纠错——**路由不靠模型猜，但模型有否决权**。

词表只收高置信业务词，泛词（安排、调整、变化、今天、明天、后天）故意不收录，因为它们在几乎每条请求里都出现，会把请求抢到错误场景。

**边界。** 只有日期推荐、多方案规划、风险检查三个 Skill 配了显式 allowed_tools，而且作用在“过滤模型可见 schema”这一层；要做执行硬隔离，得在 dispatch 前再复核。

## 3.4 白名单能防越权调用吗（B 高频）

> 只能防一部分。当前白名单控制模型看见哪些工具，能减少误选和上下文体积；但模型返回工具名后，执行分支是通过全量 Registry 查的，没有再次检查它是否属于当前允许集合。
>
> 所以准确说法是“可见性过滤”，不是“执行权限”。要升级成硬边界，就在任何 preview 或 execute 之前再校验一次工具许可、资源权限和剩余额度。

**一句话。** Prompt 指导行为，服务器控制权限。

## 3.5 模型传错参数、编出不存在的 ID 怎么办（A 必问）

> 分三层处理。**参数是坏的 JSON**：在 Provider 层就拦下，不退化成空字典，而是带上原始片段和“重写整段”的提示回传给模型，连续两次就转无工具总结。**形状不对**（字段名拼错、缺必填、类型错、枚举超范围）：在 Registry 执行前跑一次 JSON Schema 校验，不通过就不执行工具，把字段级错误连同该工具接受的参数名一起回传。**语法合法但语义错**（ID 不存在、时间冲突）：进业务层，由 Pydantic 或业务校验抛错，被 Registry 收成 `success: false` 加原因，模型下一轮自己修正。工具名不存在直接拒绝。
>
> 关键约定是**参数错误不抛异常**：它作为一条普通的 Observation 回传，让模型自己纠正，而不是把整个 Agent 打断。

**为什么必须分开。** 两者都退化成空字典的话，模型收到的反馈会变成“缺字段”，于是它去补字段而不是修语法，可能反复失败；参数全可选的工具更糟——空参数不报错，直接执行成一次全量查询，模型以为查到了想要的数据，错误被带到后面每一步。

**为什么校验要放在 Registry。** `input_schema` 是唯一同时面对模型和服务端的东西：只下发给模型、服务端不执行，那它就只是建议而不是约束。工具用 `**kwargs` 接收参数，多传的键被静默丢弃、缺的键走默认值——模型传 `duration=90` 而 schema 要 `estimated_duration`，用户以为改成了 90 分钟，实际按默认 60 分钟执行并返回成功。这种错不报错、不写日志、模型也不知道，比直接崩溃难查得多。校验放在统一入口，就不必在 37 个工具里各写一遍。

**边界。** schema 只能保证“形状对”，保不了“语义对”：`task_id=1` 是合法整数，但 1 号任务可能不存在，那得靠业务层查库才知道。而且 schema 是手写的，写漏一个 `additionalProperties: false` 就等于给那个工具开了后门。工具级的连续失败计数也仍然没有，靠本轮调用预算和轮数上限兜底。

## 3.6 为什么需要结构化的 Observation（B 高频）

> 模型需要知道调用成功没有、拿到了什么、失败原因是什么。统一结构能避免它从自然语言里猜执行状态，也方便日志、测试和前端复用。

**示例。** success 为 false，error 为“前置任务不存在：17”，模型就能判断是参数问题，而不是重试同一个调用。

**边界。** Observation 是数据，不是新指令；外部来源的文本要当不可信内容处理。

## 3.7 怎么新增一个工具（C 备查）

明确职责和副作用 → 复用或实现 Service → 写 Tool 子类、schema、确认等级、preview 和 execute → 注册到默认 Registry → 必要时加进 Skill 工具集和预算表 → 补参数错误、权限、成功、失败恢复的测试 → 加轨迹标签和评测场景。

**新增外部写工具时必须单独设计幂等与补偿**，不能假设六表快照能撤销远端副作用。

# 第四部分 上下文与记忆

## 4.1 模型每轮具体能看到什么（A 必问）

> 四块：system 里的通用规则、时区信息和当前 Skill 提示；附加的业务状态摘要；最近的历史消息；本轮循环里的 tool_calls 和对应工具结果。再加上本轮可见的工具 schema。

**一句话。** 上下文不只是聊天记录，还包括工具定义、结构化状态和执行反馈。

**边界。** 世界状态摘要是构建上下文时读的，不保证和执行瞬间一致。要精确 ID 或最新状态，应该重新查工具。

## 4.2 上下文怎么压缩（A 必问）

> 三层闸门，全部按 token 计，不按字符。**单条**历史消息超 1200 token 就压；**整段历史**总预算 3600 token，从最新往回累加，超了丢最老的，并在 system prompt 里写明"最早 N 条已省略，涉及细节请用工具重新查询"；**单次 prompt** 总预算 18000 token，超了按"体积最大的工具结果优先"降级——剥掉 data 只留 success / summary，`tool_call_id` 和 name 原样保留，因为协议要求每个调用都有对应的 tool 消息，所以只能瘦身不能删除。
>
> 压缩本身按信息密度取舍，不按位置。给每段打分：约束词（必须 / 截止 / 锁定 / 之前）+3，时间 +2，ID 和数字 +1，过短过长降权；首尾两段再加 +3 位置分，但加成只是优先权——预算真不够时首尾一样被丢，否则"必保首尾"会反过来把中间的约束句挤出去。中间按分数贪心填充，**组装完还要复核总量**，超了就从分数最低的段开始丢，而不是回头做首尾截断——后者会把刚保住的关键句拦腰切断，这个 bug 是写测试时抓到的。
>
> 结构化内容走另一条路。单行 JSON 如果按顶层逗号切段，外层往往只有三五个 key，体积最大的那个数据字段会被当成"塞不下的段"整段丢掉，最后只剩 success / summary 这类元信息；直接硬截断更糟，压出来的东西 `json.loads` 都过不了。所以 JSON 交给 `compact_payload` 逐档收紧列表保留条数和长字符串上限，每一档都还是完整对象。

**追问“会不会丢约束”。** 会，但方向和以前相反。旧实现头尾各截一刀，丢的是中间且不可控；现在约束句因为打分最高，反而优先活下来，先被丢的是纯叙述。真正救不回来的是“从没进过这 10 条窗口的早期事实”——那要靠摘要层或结构化状态，当前没做。

**边界。** 降级只处理“工具结果太大”，不处理“多个工具结果互相矛盾”；降级后模型知道有缺口但拿不到原值，得重查，多花一次调用。token 是估算值（中文按 1 字 1 token、其余 3.5 字符 1 token，再乘 1.1 安全系数），不是目标模型的分词器，跨模型有 10% 到 20% 误差。

## 4.3 字符裁剪等于 token 预算吗（B 高频）

> 不等于，这正是我们改过的地方。字符在中文和 JSON 上的 token 密度差三倍多：1800 个汉字约 1800 token，1800 个 ASCII 字符只有约 570 token。按字符设阈值，等于在中文上收紧、在 JSON 上放宽。
>
> 现在统一走 `estimate_tokens`：中文按 1 字 1 token、其余按 3.5 字符 1 token，再乘 1.1 安全系数，预算分单条 1200 / 历史 3600 / 整包 18000 三档。
>
> 但仍然不是“按目标模型精确计数”。没接 tiktoken，因为它绑定厂商分词表、体积几十 MB，对“预算控制”这个用途来说 10% 误差可以接受。真要精确，就在 Provider 层按模型注册 tokenizer，再把预算从常量改成上下文窗口的固定比例。

**不要说。** “system prompt 固定 1500 token”这类没有 tokenizer 依据的数字。

## 4.4 会话历史放进程内存，多 worker 就安全了吗（B 高频）

> 不安全，所以我把它从内存里拿掉了。原先的 `Memory` 是按 session 分桶的 dict，加锁只解决"同一进程内多个线程改坏列表"，解决不了多 worker：同一会话的第二个请求落到另一个进程，那个进程的字典是空的，模型看不到上一轮；重启同理，库里明明有记录，两边记忆却不一致。为了补这个洞还长出 `has_session` / `hydrate`——先问有没有、没有再去表里捞，本质上是把缓存一致性问题搬进了业务代码。
>
> 现在的做法是每次请求从 `chat_messages` 读最近 10 条窗口，进程内零会话状态：多 worker 天然一致，重启不失忆，也没有锁要维护。代价是每请求一次带索引的查询，换掉的是整套同步逻辑。

**一句话。** 读一致、会话串行、幂等，是三个层次；无状态只拿下第一个。

**追问怎么接。** 同一会话两个并发请求仍会各插一条 user 消息，先后由数据库决定——要严格串行得按 session_id 排队或加乐观锁，没做。

## 4.5 需要向量记忆吗（C 备查）

> 当前不需要。任务、日程、偏好都是结构化数据，查库比检索准。只有引入大量邮件、会议纪要这类非结构化内容，才需要语义检索。
>
> 真要做，也不能让模型推断自动变成永久事实：显式偏好、用户事实、临时计划和模型推断要分开存，记录来源、时间和置信度，允许用户查看和删除。

# 第五部分 循环控制与故障恢复

## 5.1 怎么防死循环和重复调用（A 必问）

> 四个维度：12 轮迭代上限、24 次普通工具执行阈值、逐工具额度、以及用工具名加规范化参数生成的调用键，拦同一 run 内的重复调用。受限调用返回结构化错误，额度耗尽的工具从后续列表移除，最后还是收不住就转无工具总结。

**逐工具额度。** 天气、事件、任务、日程查询各 3 次；规划、重排各 2 次；冲突检查、评估、方案比较、应用方案各 1 次；地点搜索和地理编码各 8 次；路线估时 12 次。

## 5.2 24 次是严格上限吗（A 必问，高频追问）

> 不是。计数在每轮工具执行后增加，总量判断在整轮 tool_calls 处理完之后，所以一个响应带多个调用时可能越过阈值。确认分支的预览和确认执行也不计入这个普通工具计数。
>
> 要做严格预算，应该在每次调用前预占额度，限制单个响应的调用数量，并把预览、执行、确认三个阶段的资源统一计算。

**参数去重的误伤。** 同一 run 内参数相同就拒绝，但“先查任务、改完再查同样的条件”是合法重查。它防的是循环，不是业务幂等。

## 5.3 模型挂了怎么办（A 必问）

> 先分类：401/403 鉴权失败停止自动尝试，等修配置后调 reconnect；429 限流和网络、超时这类瞬时故障进带抖动的指数退避。冷却期间切到本地规则 Provider，能处理部分查询、冲突检查、撤销和明确的排期请求。
>
> 核心 CRUD 和规划服务不依赖模型，所以业务还能用；但复杂语义理解会降级，地图和天气断网就不可用。

**边界。** 这不是后台一直重试，而是后续请求到来时判断冷却是否到期，到期才有机会切回真实模型。

## 5.4 退避公式是什么（B 高频）

基础等待是 60 乘 2 的（连续失败次数减一）次方，上限 600 秒；实际等待再加 0 到基础值 20% 的随机抖动。所以基础序列是 60、120、240、480、600，加抖动后最长可到 720 秒。

**不要说。** “实际等待严格不超过 600 秒。”也不要说已经实现了完整的 CLOSED/OPEN/HALF_OPEN 熔断器。

## 5.5 工具报错会让整个 Agent 崩吗（B 高频）

> Registry 捕获普通工具异常，转成失败结果，让模型有机会改参数或换策略。但它不等于覆盖所有异常来源，也不会自动修复一个已经进入失败状态的数据库 Session。

**要分清。** 模型接口失败由 Provider 和 Loop 处理；参数和业务失败由 Tool、Service、Registry 处理；确认批次失败由快照补偿；进程崩溃和资源耗尽当前没有完整恢复。

## 5.6 一次请求最坏要等多久（C 备查）

> 单次模型调用超时 30 秒，12 轮迭代，理论上限约 6 分钟，还没算最后一次总结调用。复杂排期还要加 CP-SAT 每次 5 秒、最多 13 轮校验重求，真实耗时在十几秒量级。
>
> 当前没有请求级总 deadline，也没有流式输出，前端只能等完整响应。这是体验上最大的短板，也是我下一阶段要补的第一块。

**说这段的好处。** 自己把最难看的地方算清楚，比被问出来强。

# 第六部分 写操作安全（差异化最强的一块）

## 6.1 危险操作怎么确认（A 必问）

> 对删除、重新规划这类操作，Agent 不立即执行，先展示准备改什么，让用户确认。同一轮多个待确认操作合并展示，用户只点一次。工具名、参数、摘要和预览一起落 pending_actions，确认后再逐个执行。

**确认等级。** none 是只读，auto 是执行后记录变更，confirm 是先预览再执行。注意 generate_plan 是 auto 不是 none——它写的是 proposed 日程，仍然落库。

**两个别混。** Agent 确认是批准一批动作；Schedule 从 proposed 到 accepted 是业务状态流转。这是两件事。

## 6.2 批次中途失败怎么办（A 必问）

> 执行前把六张核心业务表整体序列化成快照：任务、事件、任务依赖、日程、用户偏好、计划版本。然后逐项执行确认工具。某项失败就停止后续，先回滚当前未提交事务，再按外键顺序删除这六张表的全部行，按相反顺序重灌快照，最后提交。

**顺序。** 快照 → 执行 A → 执行 B → B 失败 → 停止 → 回滚未提交 → 删子表父表 → 清身份映射 → 先父后子重灌 → 提交。

**边界。** 保护范围是“用户这次确认的这一批操作”，不是整段会话；执行后审计发现冲突只提示，不自动恢复。

## 6.3 能撤销已经提交的写入吗（A 必问，本文件最关键的一题）

> 能，但机制要讲准。restore 的第一步是 rollback 丢掉未提交改动，然后按外键顺序删除六张表的全部行，再把快照重灌进去、提交。所以即使某个工具中途自己 commit 过，它的写入也会在“删全表”这一步被抹掉。
>
> 这不是事务，是整表覆盖式回滚。代价有三个：没有隔离性，恢复期间别的请求写这几张表会被覆盖；进程崩在“已提交但还没补偿”的窗口里就没人恢复；六张表之外的外部副作用撤不了。

**可以主动讲的一句。** 这段代码的原注释写错了，它说“工具提前 commit 就救不回来”，但测试 test_restore_rolls_back_partial_insert 明确验证了 commit 之后仍能恢复成快照状态。因为 restore 走的是删全表重灌，不是 rollback。我是按测试的实际行为修正理解的。

**为什么这句值钱。** 大多数候选人只会复述注释。你说“我的注释和测试矛盾，我发现了，而且我知道哪个对”，可信度直接上一档。

## 6.4 为什么不直接用事务或 SAVEPOINT（A 必问）

> 统一事务是更合适的方向，当前障碍是已有 Service 各自 commit，需要先调整事务边界。SAVEPOINT 可以做局部回滚，但要正确管理外层事务和嵌套事务，不能在内部随意提交整个 Session。
>
> 所以现在的补偿是过渡方案：能用，但成本和表总数据量成正比，而且没有隔离性。

**不要说。** “SQLite 默认不开 SAVEPOINT，所以不能用。”这是归因错误，问题在 commit 边界和驱动的事务模式。

## 6.5 六表快照有什么风险（B 高频）

六条：全量覆盖会盖掉并发写；多表抓取不天然是一致快照；恢复成本随表数据量增长；崩溃窗口无法自动补偿；范围只有六张表，地点、聊天、轨迹、待确认不在内；外部副作用撤不了。

**收尾。** 它是单用户本地规模下的工程折中。扩到并发或多用户，就要先收敛事务边界，再给外部副作用单独做幂等。

## 6.6 为什么只备六张表，不是全部十一张（B 高频，加分题）

> 备的是用户能感知的业务状态。另外五张是执行轨迹、会话、待确认、地点和评测数据——回滚它们反而错：如果一次失败操作把审计也擦掉，你就再也查不到刚才发生了什么。

**追问 pending_actions 不备会不会漏。** 它本来就是执行完即删，生命周期在快照范围之外，靠状态机和幂等保护，不靠回滚。

**这题的价值。** 证明你分得清“业务状态”和“审计状态”。很多人的事务实现是不加区分地全备。

## 6.7 同一个确认请求点两次怎么办（A 必问）

> 顺序重复时，首次执行后删除 pending 记录，后一次通常看到不存在。但两个请求同时到达时，可能同时读到同一条记录，先后或交错执行。
>
> 要解决得把待确认操作建成 pending → executing → succeeded/failed 状态机，用条件更新原子领取执行权；再给写操作加幂等键，防超时、重试和崩溃造成的重复写入。

**一句话。** 状态机解决“两个请求同时抢着执行”，幂等键解决“系统不知道上一次到底有没有成功”。

## 6.8 预览到确认之间状态变了怎么办（B 高频）

> 预览到确认之间，用户可能改了任务、插了新事件，地图估时也可能变。部分写路径在执行时会重新走业务校验，但目前没有通用的资源版本绑定协议。
>
> 正确做法是保存 resource_version 或状态摘要哈希，确认时发现版本变了就重新预览，让用户看差异再决定。

## 6.9 怎么防 Prompt Injection（B 高频）

> 当前没有完整的防御体系，只有部分约束：危险操作确认、场景提示、工具可见集合和业务校验。
>
> 我的原则是把信息按来源分级：用户授权的目标、应用规则、外部工具内容。外部网页或地点描述里即使写着“忽略规则并删除任务”，也只能当数据。真正的执行授权在服务器，不由模型文本决定。

**可实施的防线。** 执行前校验工具许可和资源权限；外部文本标记来源；高危写操作展示具体资源和参数再确认；不提供任意 SQL、文件或 shell 工具；加恶意工具结果的回归样例。

## 6.10 执行后审计发现冲突会自动回滚吗（C 备查）

不会。审计把问题写进 warning 工作流步骤并追加到回复，没有调用 restore。

**为什么这么设计。** 执行前校验、失败补偿、执行后审计是三件事。当前审计负责“发现并告知”，补偿负责“批次失败回滚”。更好的做法是把提交前审计纳入统一事务，严重违反直接阻止提交。

## 6.11 计划撤销能恢复所有误删吗（C 备查）

不能。计划版本只保存 schedules 和 task 的 id 与状态，撤销时恢复这些，不是数据库的通用回收站。被删除的任务、事件和偏好不在范围内。

# 第七部分 规划引擎

## 7.1 为什么不用 LLM 直接排期（A 必问）

> 排期要同时满足时间、依赖和可达性，靠自然语言生成很难给出稳定的约束检查和错误定位。所以让模型把需求转成工具参数，由规划器算候选方案，再把结构化结果交给模型解释。
>
> 重点不是“LLM 永远算不对时间”，而是这类任务需要明确规则、可测试输出和可控执行。

**边界。** 不要说“换模型结果绝对不变”。模型可能生成不同参数；准确说法是“相同结构化输入和外部条件下，业务计算不依赖模型版本”。

## 7.2 CP-SAT 怎么建模（B 高频）

> 对每个任务和候选起点建布尔变量，表示这个任务是否在这个时刻开始；用可选固定长度区间表达占用，固定忙碌区间也放进模型。约束有四类：每个任务最多选一个候选；区间之间 NoOverlap；前置未安排则后置也不能安排；违反前后顺序的候选对不能同时选。
>
> 目标最大化加权分数：策略权重、安排的工作量、是否落在偏好窗口，再减一个起点惩罚让结果倾向早安排。

**为什么允许任务不安排。** 容量可能真的不够。允许未安排，可以输出部分可行计划和明确失败原因，而不是整个模型直接不可行。

## 7.3 一定全局最优吗，5 秒一定返回吗（B 高频）

> 不一定。OPTIMAL 才表示模型内已证明最优，FEASIBLE 只表示找到可行解，当前代码两种都接受。所以我说“全局优化搜索”，不说“每次都是最优解”。
>
> 5 秒是每次 Solve 的预算，外层还有最多 13 轮业务校验重求，另外有建模和外部调用耗时。整个接口不是 5 秒硬上限。

## 7.4 求解失败怎么降级（B 高频）

> 当前主要对优化器抛出的 RuntimeError 回退贪心，比如没装 OR-Tools、任务不支持拆分。求解器返回 UNKNOWN 或 INFEASIBLE 时不一定抛异常，可能返回空安排，所以并不是所有失败都会自动降级。
>
> 改进方向是返回明确的求解状态、目标值、耗时和失败原因，再决定回退贪心、缩小范围还是直接告诉用户排不下。

## 7.5 目标函数是什么（C 备查）

每个候选的分数大致是：规划权重，加时长刻度乘 20，加 180 的偏好窗口奖励，减起点刻度的惩罚项。模型最大化被选候选的总分。

**边界。** 这是启发式加权，不是严格的多目标字典序。不能声称“低优先级绝对压不过高优先级”而不证明权重上界。

## 7.6 地图约束怎么和求解器结合（C 备查）

> 当前是求解后校验。先生成候选方案，再用校验回调检查通勤；发现某个任务的某个起点不合法，就把它加入禁用集合，重新求解。

**两个边界。** 禁掉的是“任务—起点”，可能比只排除某组冲突更强，从而误伤其他可行组合；外层迭代用尽后，当前返回最后一次结果，没有统一的“必须全部校验通过”出口。

## 7.7 时间不重叠但赶不及怎么检测（C 备查）

> 普通相邻活动，用下一活动开始减上一活动结束，算可用通勤时间，再和路线估时比较。如果后一段本身就是 travel，就用它的结束时间当最晚到达，出发时间取上一段结束和 travel 开始里的较晚者。
>
> 地图不可用时标记“未校验”，不假装通过。

**缓存 TTL。** 路线 5 分钟，地点搜索 24 小时，地理编码 30 天。路况会变，地址到坐标几乎不变，所以三档分开。

## 7.8 贪心和 CP-SAT 什么时候用哪个（C 备查）

> 自动模式看复杂度信号：待安排任务至少 6 个、跨度至少 3 天且任务至少 3 个、至少 2 个截止时间、至少 3 个地点、至少 2 项有依赖。命中倾向优化模式，否则走贪心。
>
> 快速和深度的区别是搜索方式和支持范围，不是“快速就可以忽略硬约束”。

# 第八部分 测试、评测与可观测

## 8.1 怎么测试一个 Agent（A 必问）

> 分两层。第一层测框架本身：用 Mock 模型预先指定每一轮返回什么，比如先查任务再改任务，或者故意重复调用，然后断言系统是否正确执行、是否触发确认、是否拦住重复、失败后是否恢复数据。模型输出固定，所以结果可复现。
>
> 第二层测真实模型的决策：给固定请求集，看它能否选对工具、填对参数、在删除前要求确认，最终让数据库达到预期状态，同时记录完成率、错误操作、调用次数和延迟。

**为什么看最终数据库状态。** 同一个任务可以有不同的正确路径。先查全部事件还是按日期查都可以，只要最后删对了、没越权，就应该算成功。

## 8.2 五个评测场景是什么，用真模型了吗（A 必问）

> 五个场景：紧急任务规划、旅行行程创建、行程整体顺延、批量事件删除、冲突查询。全部使用 MockProvider，在隔离的内存数据库上跑，重点验证工具执行链路、确认流程和业务状态。
>
> 它能证明整条链路是通的，不能证明真实大模型的理解准确率。下一步才是注入真实 Provider、扩请求集、统计成功率和失败类型。

## 8.3 236 个测试能证明什么（B 高频）

> 证明覆盖范围，不证明覆盖率或线上质量。比较有代表性的几类：确认批次失败后回滚、迭代上限后转无工具总结、额度耗尽的工具从下一轮移除、任务依赖拒绝成环、锁定日程在局部重排中保留、CP-SAT 找到贪心错过的全局顺序、Skill 路由的排序键与切换预算（其中 22 条专测关键词路由和模型自选）。
>
> 我没有跑覆盖率报告，所以不会说“覆盖了所有边界”。

## 8.4 真实模型评测怎么设计（B 高频）

> 先建独立的开发集和保留集。每个样例给定数据库初态、用户请求、允许的行为和目标状态。模型可以走不同合法路径，判定以业务状态和安全约束为主，同时记录轨迹质量、延迟和费用。
>
> 样例要分层：基础意图、多步组合、多轮指代、歧义、安全、故障、状态变化。固定模型版本、配置、prompt、时钟和数据库初态，每类重复运行，报告均值和失败类别。

**怎么避免过拟合。** Mock 集负责机制回归；真模型集不预设 tool_calls，只定义目标状态和禁止的副作用；保留一部分没参与 prompt 调整的样例。

## 8.5 线上怎么定位错误、控制成本（B 高频）

> 当前记录工具阶段、状态、耗时、模型 token 和估算费用，可以回看失败步骤。进一步要按 run_id、step_id、tool_call_id 关联模型与工具调用，记录错误分类、重试和脱敏参数，并建立请求总 deadline 与 token、费用预算。
>
> 现在能统计用量，但没有完整的费用硬限额，也没有逐步崩溃恢复。

**三个别混。** 可观测不等于可恢复；费用估算不等于精确账单；次数预算不等于延迟预算。

## 8.6 token 和费用怎么算（C 备查）

输入 token 数除以一百万乘输入单价，加输出 token 数除以一百万乘输出单价。当前根据 Provider 返回的 usage 和本地配置单价估算。

**边界。** 上游没返回 usage、缓存计价、特殊 token、失败仍计费，都会让估算和账单不一致。可以说“记录 token 并估算成本”，不能说“精准账单核算”。

## 8.7 执行轨迹记录了什么（C 备查）

> AgentRun 记录会话、请求、Provider、Skill、状态、耗时、确认信息、步骤 JSON、token 和费用。步骤包含工具名、阶段、状态、摘要和部分耗时。
>
> 它适合运行回看，还不是完整的分布式 tracing，也不保证保存每个工具的完整输入输出。

# 第九部分 数据与后端

## 9.1 Task、Event、Schedule 为什么分开（B 高频）

> Task 是要做的工作和它的约束，比如写论文、预计 180 分钟、周五截止；Event 是已经确定时间的外部安排，比如周三下午组会；Schedule 是为某个任务生成的执行时间块。
>
> 分开的原因是“要做什么”和“什么时候做”是两件事。一个任务可以拆成多段日程，重排时只换日程不动任务。

**边界。** Event 在规划时是不可移动约束，但用户仍可显式编辑；“规划器不能移动”不等于“任何情况下不可修改”。

## 9.2 一共有多少张表（B 高频）

十一张：tasks、task_dependencies、events、schedules、user_preferences、saved_locations、plan_versions、pending_actions、chat_messages、agent_runs、evaluation_runs。

**两个容易答错的点。** dependency_ids 是从关系算出来的属性，不是 tasks 表里的列；trip_id 是行程分组标记，不代表还有一张 trips 表。

## 9.3 时间和时区怎么处理（B 高频）

> 存储约定是 naive UTC。业务服务把带时区输入转成 UTC；工作时段和午休用用户偏好时区加 ZoneInfo 转成 UTC 窗口。

**必须自己说的两个缺口。** 工具序列化通常显式加 Z，但普通 API 的 datetime 字段不都加；主日历用浏览器时区渲染，不是严格按偏好时区。所以“改偏好后所有时间立刻按新时区显示”不成立。

**再追 DST。** 工作窗口按目标日期用 ZoneInfo 转，比固定加减小时好；但 Agent 提示里的偏移量用当前日期的整数小时，表达不了半小时时区和跨日期的夏令时变化。

## 9.4 为什么用 FastAPI、SQLAlchemy、SQLite（B 高频）

> FastAPI 便于用 Pydantic 定义输入输出、自动生成接口文档；SQLAlchemy 把业务对象和数据库操作组织起来；SQLite 适合本地单用户，安装成本低。这个组合让我把主要精力放在 Agent 和业务规则上。

**权衡要主动说。** 同步网络和求解会占请求线程；SQLite 不适合高并发写；当前没有生产级鉴权和迁移体系。

## 9.5 多 worker 能直接扩容吗（C 备查）

不能。pending actions 在数据库里可以跨 worker 读到，会话历史也是每请求从 `chat_messages` 读的；但模型故障状态、待确认操作的内存结构和缓存仍是进程内的。直接加 worker，不等于会话串行、确认幂等和故障状态共享已经解决。

## 9.6 数据迁移和依赖管理有什么不足（C 备查）

> 启动时 create_all 建缺失表，再用 ensure_schema 给旧表补列。这是轻量兼容逻辑，不是完整的迁移版本管理。下一步是 Alembic、升级前备份和迁移测试。
>
> requirements 主要设最低版本，没有锁可复现依赖；测试还需要额外包，所以不能说“只装五个库就能跑全部测试”。

## 9.7 要部署到公网，首先做什么（C 备查）

> 先补认证授权和资源归属，再处理会话隔离、确认幂等、限流、密钥管理、日志脱敏和数据库备份。

**两个现状。** 启动脚本默认监听 0.0.0.0，CORS 放开；模型调用会把上下文发出去，地图会把地点发出去。所以“本地优先”不等于“默认只监听本机”。

# 第十部分 架构选型与扩展

## 10.1 项目需要 RAG 吗（B 高频）

> 当前不需要。任务、日程、偏好都是结构化状态，直接查库更准。引入大量邮件、会议纪要或文档之后，才需要 RAG 定位证据。
>
> 而且两种需求不一样：新邮件到了要抽待办，是增量抽取，不一定需要检索；用户问“上次导师说的截止时间是什么”，才需要跨历史内容找证据。

**核心态度。** 从业务瓶颈决定架构，不为关键词加组件。

## 10.2 需要多 Agent 吗（B 高频）

> 当前不需要。单 Agent 加工具和 Skill 已经能表达主要流程。只有子任务能独立分工，而且收益超过通信、状态同步和错误恢复成本时，才值得拆。
>
> Skill 是同一个 Agent 的策略配置，不是多个独立 Agent。

## 10.3 MCP 能用在哪里（B 高频）

> MCP 可以统一工具和资源的接入协议。当前工具在进程内调用，接入成本已经很低；如果希望其他客户端复用 PlanPilot 的能力，或者接第三方服务，就值得加一层 MCP server 适配。

**边界。** 它不替代模型推理、业务校验、授权和幂等。协议统一了，服务端仍然要控制副作用。

## 10.4 流式输出怎么加（B 高频）

> 当前没有 SSE，对话接口一次返回完整 JSON。要加的话，先分清两种流：业务进度流和模型文本流。
>
> 业务进度流推“识别请求、查询任务、等待确认、完成”这些阶段，收益最大，因为用户最怕的是不知道系统在干什么。模型文本流要等工具参数收齐才能执行，确认预览必须区分“计划执行”和“执行成功”。

**工程细节。** 断线重连按事件序号补发，不要重放写工具。

## 10.5 换更便宜的模型怎么验证（C 备查）

> 先检查协议和工具调用能力，再用同一评测集比较任务成功率、参数合法率、确认违规率、平均轮次、p95 延迟和费用。
>
> 不能只看单 token 单价，小模型多走几轮可能更贵。

## 10.6 如果加 Plan-and-Execute 怎么设计（C 备查）

Planner 生成结构化步骤、依赖和预期效果 → Validator 检查工具许可、必要参数和风险 → Executor 执行并记录结果 → 失败按错误类别决定重试、重规划还是问用户 → 写步骤在确认后执行，执行计划和预览绑定。

**要区分。** 项目里的“规划”是规划用户任务的时间，不是规划 Agent 的执行 DAG。

## 10.7 用户关掉页面，Agent 应该怎么办（C 备查）

> 当前没有持久执行和取消协议。要做得区分三类：可取消的只读工作、已确认的写动作、已经提交的结果。
>
> 长任务可以用任务 ID、状态表和后台 worker。取消后停止新步骤；正在执行的外部写入要么查询结果，要么补偿，不能只把页面状态改成“已取消”。

# 第十一部分 行为面与反问

## 11.1 最大的技术难点是什么（A 必问，STAR）

> 场景是 Agent 会连续执行多个写工具，单步成功不等于整体成功。比如第一个删除完成、第二个失败，用户就拿到一个没预期的中间状态。
>
> 我做了批量确认和执行前六表快照，失败整体补偿。继续梳理又发现补偿没有原生事务的隔离性，也不能处理崩溃窗口，所以后续优先统一提交边界，再给写操作加幂等键。

**追问就定位代码。** 确认分支在门面的 _handle_confirmation，快照在 transaction.py 的 capture 和 restore，测试是 test_restore_rolls_back_partial_insert。

**注意。** 具体怎么发现、花了多久、有没有线上影响，只能按真实经历补，不要编。

## 11.2 面试官说“你这个就是调 API”（B 高频）

> 调模型 API 只是其中一个环节。更多工作在于把模型动作接进业务系统：设计任务和日程的数据模型、实现多步工具循环、处理确认与部分失败、把时间和通勤约束交给规划器、建立可回归的测试。
>
> 您希望我从 Agent Loop 还是从多步写入的恢复机制展开？

**要点。** 邀请对方深入你有证据的部分，不贬低 demo，也不吹“几天就能写完别人的项目”。

## 11.3 面试官指出你代码有问题（B 高频）

> 我先确认触发条件和当前保证的范围，再沿执行路径检查。如果确实存在，我会写一个失败用例固定它，修复后跑相关回归，再更新原来的能力描述。

**可以主动举的例子。** 白名单不能防模型伪造工具名，这是成立的：当前只过滤输入给模型的列表，下一步要在执行前再校验，并用脚本化模型返回越界工具来验证拒绝执行。

## 11.4 AI 辅助编码用了多少（B 高频）

按事实答，不掩饰也不虚构贡献。推荐结构：用 AI 辅助哪个环节，自己负责哪些设计、审查、调试和测试；能解释关键控制流、数据模型和失败路径；对生成的代码和注释做过核实。

**可以举的例子。** 事务注释曾把“提交后的 rollback”和“快照补偿重写”混在一起，我是通过实际代码和测试设计区分这两者的。

## 11.5 科研和 Agent 工程怎么联系（C 备查）

> 科研训练了我设计实验、拆解目标和分析失败案例的能力；Agent 项目让我把这些能力用在完整系统里，处理接口、状态、执行和评测。
>
> 我不想硬说两个项目在技术上是同一件事，但“提出假设、设计对照、看失败样本”的方法是共通的。

## 11.6 反问什么（B 高频）

准备三个，问两个：你们现在的 Agent 怎么评测，是人工看对话还是有确定性回归集；这个岗位的实习生三个月做到什么程度算达标；团队当前最大的卡点是模型效果还是工程可靠性。

**别问。** 转正比例、加班、能不能远程，这些留到 HR 面或 offer 阶段。

# 附录

## 名词速查

按一次请求的顺序排列。术语不是必须说，但被问到要答得出——第一次出现时顺手解释半句，比连报三个名词更可信。

**Pydantic** —— Python 的参数检查库。字段类型不对就直接拒掉请求，业务代码根本不会被执行。

**session_id** —— 一段对话的编号。前端带上来，后端才知道是同一个人在接着说。

**门面** —— 统一入口函数。对外只有一个方法，内部自己决定该走哪条路。

**回灌** —— 把数据库里的历史读回内存缓存。只在服务重启、内存空掉时才需要。

**system prompt** —— 每次请求都放在最前面的长期规则，告诉模型它是谁、要守什么约束。

**工具 schema** —— 给模型看的工具说明书。模型看不见代码，只看得见这份说明。

**tool_calls** —— 模型返回的结构化调用申请，包含要调哪个工具、参数是什么。

**Observation** —— 工具执行完的结果，原样回传给模型，让它继续判断。

**轮次** —— 一次“问模型”算一轮。本项目最多 12 轮。

**confirm 等级** —— 工具的危险度分级：只读、直接执行、必须用户确认。

**预览** —— 只计算执行后会变成什么样，不写入数据库。

**pending_actions** —— 存待确认操作的数据库表。用户点头之后才真正执行。

**快照** —— 执行前把相关几张表整个备份一份。中途失败就按依赖顺序还原回去。

**原子性** —— 一批操作要么全部成功，要么全部当没发生，不允许改了一半。

**数据库会话** —— 和数据库之间的通道。改动先攒在内存里，提交时才落盘。

**commit** —— 真正写进数据库文件的那一下。

**token** —— 模型的计费单位。中文大约一个字对应一到一点五个。

**幂等** —— 同样的调用重复执行，结果不变，也不会产生重复数据。

**白名单** —— 只允许清单里的工具对模型可见。

**执行后审计** —— 改完数据再查一遍，看有没有产生时间冲突。

| 普通工具总量 | 24 次 | 轮末检查，不是逐次硬上限 |
| 历史条数 | 10 条 | 整段预算 3600 token，单条上限 1200 token |
| prompt 总量 | 18000 token | 超了按体积降级工具结果，只瘦身不删除 |
| 会话历史窗口 | 最近 10 条 | 每请求从 `chat_messages` 读，进程内无状态 |
| 待确认 TTL | 600 秒 | 超时失效 |
| 模型单次超时 | 30 秒 | 12 轮理论上限约 6 分钟 |
| 退避 | 60 至 600 秒，抖动 0 至 20% | 实际最长约 720 秒 |
| CP-SAT | 每次 5 秒，最多 13 轮重求 | 不是接口总耗时 |
| 缓存 TTL | 路线 5 分钟、地点 24 小时、地理编码 30 天 | 按数据变化频率分档 |
| 规模 | 37 工具、10 Skill、236 测试、5 场景、11 表（备 6 表） | 静态事实 |

## C 八条“不等于”

白名单不等于执行权限；调用去重不等于业务幂等；读窗口无状态不等于会话串行；pending 落库不等于并发只执行一次；补偿恢复不等于原生事务；执行后审计不等于自动回滚；FEASIBLE 不等于已证明最优；Mock 回归不等于真实模型效果。

## E 五条追问链

**工具安全。** 为什么需要白名单 → 在哪过滤 → 模型伪造被隐藏的工具怎么办 → 确认阶段还校验吗 → 提示注入怎么绕过模型侧约束 → 怎么测服务器真的没执行。

**事务。** 为什么用补偿 → commit 过还能撤吗 → 其他请求写入会被覆盖吗 → 进程崩溃怎么办 → 外部日历写入怎么撤 → 怎么设计统一事务和幂等。

**记忆。** 模型看哪些上下文 → 为什么是 10 条 → 截断丢了约束怎么办 → 工具历史持久化吗 → 多 worker 一致吗 → 什么时候才需要语义记忆。

**评测。** 236 个测试测了什么 → Mock 能证明模型效果吗 → 真实评测怎么设计 → 路径不同算错吗 → 怎么测确认安全 → 怎么避免调 prompt 过拟合。

**规划。** 为什么用求解器 → 变量和目标是什么 → FEASIBLE 和 OPTIMAL 差在哪 → 地图约束怎么接进去 → 13 轮后还不合法怎么办 → 总时间预算怎么设。
