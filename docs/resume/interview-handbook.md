## 第 2 章 架构与真实请求链路

> 这章只要记住：一条完整链路 + 三个分流点（普通 / 确认 / 降级）。

### Q06 整体架构
【答】前端原生 JS → FastAPI → 两条路：普通业务路由直连 Service；Agent 路由经 Agent 门面 → Loop → Skill / LLM / Tool Registry → Service → SQLAlchemy / 规划引擎 / 地图天气 → SQLite。
【别】别说"Agent 是所有 service 的上层"——普通 API 可以直接调 service，Agent 只是复用同一套业务能力。

### Q07 为什么 API / Tool / Service 分层
【答】API 管 HTTP；Tool 管给模型的能力描述、参数入口、确认等级、可读结果；Service 管可复用业务规则和落库。同一能力前端和 Agent 走同一套规则，避免两套逻辑漂移。
【别】别说"HTML 转义放在 tool 层"——输出编码属于渲染边界。

### Q08 一次请求的完整路径
【答】校验请求 → 生成或复用 session → 内存没有就从 `chat_messages` 恢复文本 → 门面分流（普通 / 确认）→ 循环里选 Skill、构建 prompt 与状态摘要 → 模型返回文本或工具调用 → 需确认则落 pending 并返回预览 → 门面做执行后审计 → 汇总状态、耗时、token、估算成本，记 Run 与消息。
【界】轨迹是在一次 handle 返回后统一记录的，进程中途崩溃不能保证每步都留痕。

### Q09 Loop 怎么跑
【答】每轮把上下文 + 可见工具 schema 发给模型；返回文本就结束；返回 tool_calls 就逐项检查存在性、重复、额度，再预览或执行，把结构化结果回传，进入下一轮；到阈值转无工具总结。
【码】`loop.py:153` 起。
【界】12 轮之外可能再加一次总结调用，所以不等于 HTTP 请求必须 ≤12 次模型调用。

### Q10 算 ReAct 还是 Function Calling
【答】按 ReAct 的"推理—行动—观察"组织闭环，动作由原生 Function Calling 表达。
四层分清：ReAct 是组织思路；Function Calling 是接口机制；Agent Runtime 是调用执行预算终止；Workflow 是确认与补偿这类固定流程。
【界】Function Calling 模式下模型不一定输出完整思考链，不宣称"思维链全可见、全持久化"。

### Q11 为什么这算 Agent 不是工具路由
【答】下一步动作不由固定代码决定：模型根据需求和工具反馈选择查什么、改什么、何时停。路由只是第一步，后面是多步决策 + 观察反馈。
【界】核心排期是确定性业务工具，不需要模型逐分钟搜索时间。

### Q12 一个真实的多步例子
【答】"论文比较急" → `get_tasks(q="论文")` → `update_task(priority="high")` → `generate_plan(days=7, gap_minutes=30)` → 总结。
【界】这条普通链没有会话级回滚：前面 update 成功、后面规划失败，优先级已经被改。六表快照只保护确认批次。

### Q13 有哪几种状态
【答】四层分开：会话上下文（`chat_messages` 历史 + `user_preferences` 偏好）、单次运行（局部变量 + `AgentRun`）、模型服务状态（进程内 ok / transient / rate_limited / auth_failed）、业务实体状态（Task pending、Schedule proposed）。
【界】做可恢复执行要把游标、已完成工具、待确认步骤持久化，光存最终文本不够。

## 第 3 章 Tool Calling 与 Skill

> 这章只要记住：Registry 找工具、Tool 接模型、Service 办事；白名单不是权限。

### Q14 Tool Registry 设计
【答】每个工具声明 name / description / input_schema / output_schema / confirmation / execute / preview，返回统一 `ToolResult`（success、data、error、summary、needs_confirmation）。Registry 负责注册、查找、给模型产出 schema、统一捕获异常。
【界】发给模型的只有 name、description、`parameters=input_schema`；`output_schema` 声明了但没有统一下发、也没有输出校验。

### Q15 为什么要结构化 Observation
【答】模型必须知道成功与否、拿到什么、为什么失败。统一结构避免它从自然语言里猜状态，也便于日志、测试、前端复用。
【界】Observation 是数据，不是新指令；外部来源文本要按不可信处理。

### Q16 模型怎么知道有哪些工具
【答】Registry 汇总 JSON Schema，Loop 按场景白名单和额度耗尽情况过滤后下发。模型只输出工具名和参数，执行由应用代码做，模型不碰数据库。

### Q17 37 个工具怎么分类
【答】场景理解 1 ｜ 任务 6 ｜ 事件行程 9 ｜ 日程 5 ｜ 规划分析 9 ｜ 偏好 2 ｜ 时间天气 2 ｜ 地图 3。
【别】分类没有行业标准，别把它当卖点，重点是"工具数量与职责边界"。

### Q18 工具粒度怎么取舍
【答】读工具可以细，便于组合；有强一致性要求的写操作要按业务意图封装，例如整组行程修订用 `revise_trip`，而不是让模型反复 `update_event`。
判断标准：是否构成一个业务意图、是否需要共同校验与共同提交。

### Q19 Skill 和工具的关系
【答】Tool 是可执行能力，Skill 是场景策略：name、description、keywords、system_hint、allowed_tools、priority。
10 个 Skill：日期推荐、多方案规划、风险检查、任务理解、日程规划、重排、天气规划、旅行规划、每日规划、冲突解决。
另有一个 `select_skill` 工具，让模型能自己列举并切换场景——它不算业务工具，永远对模型可见。
【界】只有 3 个配了 `allowed_tools`（日期推荐、多方案、风险检查），其余靠提示词。

### Q20 路由算法
【答】两层。第一层是**关键词先验**：要求命中至少一个关键词，再按 `(priority, 命中词总长度, 命中词数量, -注册顺序)` 排序，**第一比较项是优先级，不是命中数量**。第二层是**模型自选**：关键词没命中，或者命中了但不符合真实意图，模型调 `select_skill` 按 name 覆盖，不再走关键词匹配；切换次数单独限 3 次且不占业务调用预算。
词表只收高置信业务词，泛词（安排 / 调整 / 今天 / 明天 / 后天）故意不收录——它们几乎出现在每条请求里，会把请求抢到错误场景。
【界】路由已有 22 条测试（14 条关键词路由 + 8 条模型自选），覆盖排序键、白名单收窄、切换幂等与次数上限；但样本是自建的，不是线上分布。扩场景时应该先扩这个集，再比关键词 / Embedding / 小模型。

### Q21 白名单真能挡越权调用吗
【答】不能，现在只挡"模型看见什么"。`_available_tool_schemas()` 过滤 schema，但执行分支走全量 Registry，没有复查 `active_tool_names`。
【界】要升级成硬边界，得在 dispatch 前校验工具存在性、场景许可、用户权限、剩余额度；确认阶段还要复核。
【别】别说"白名单实现了权限隔离"——这是安全上的真 gap。

### Q22 参数校验
【答】三层：结构（类型、必填、枚举、长度）→ 业务（结束晚于开始、依赖存在、无环、地点合法）→ 授权与状态（有权操作、版本未变、确认未失效）。当前部分写工具用 Pydantic，Service 再查业务规则，Registry 把异常转成失败结果。
【界】Registry 本身没有统一执行 JSON Schema 校验。

### Q23 结构化输出的边界
【答】Provider 解析 `function.arguments`；JSON 解码失败会回退成 `{}`，等于把"非法 JSON"变成"缺字段"，丢了错误类别。
【界】`structured()` 用 JSON object 模式，但没拿 `output_schema` 做严格校验，也不是主路径。

### Q24 同轮多个工具怎么处理
【答】串行：普通工具直接执行，需确认的先预览并收集，本轮合并成一个待确认批次。
【界】① 多 tool_calls 不等于并行；② 确认只合并本轮，不是整段会话；③ 同轮混合时，普通写工具可能已生效，用户拒绝后面的确认不等于撤销前面的。

### Q25 怎么新增一个工具
【答】定职责与副作用 → 复用或新增 Service 方法 → 写 Tool 子类（schema、确认等级、preview/execute）→ 注册到 `build_default_registry()` → 视需要加进 Skill 白名单和提示词 → 补参数错误 / 权限 / 成功 / 失败恢复的测试 → 加轨迹标签与评测场景。
【界】新增外部写工具必须单独设计幂等与补偿，六表快照撤不了远端副作用。

## 第 4 章 上下文与记忆

> 这章只要记住：模型看到的 ≠ 数据库；裁剪是近似，会丢约束。

### Q26 模型每轮看到什么
【答】system（通用规则 + 时区 + 当前 Skill 提示）、附加的业务状态摘要、最近历史、当前循环的 tool_calls 与 tool messages、本轮可见工具 schema。

### Q27 世界状态摘要的作用
【答】让模型知道当前时间、偏好、任务、事件、已有安排，作为起点；细节仍靠工具查。
【界】摘要 ≠ 完整数据库，且是构建时读取的，不保证和执行瞬间一致。

### Q28 记忆是分几层的
【答】三层，边界按"谁负责正确"划。
层一 `chat_messages` 全量流水，只增不改、不进提示词，每次请求读最近 60 条窗口（保留 10 条原文）；层二 `session_summaries` 滚动摘要——溢出满 8 条就把老的折成五段（约束/决定/纠正/悬置/实体），400 token 封顶，`covered_to_message_id` 只前进，模型不在线时降级成确定性压缩；层三再分三区：规则区是 `context.py` 的代码常量（模型只读）、偏好区是 `user_preferences`、事实区是 `memory_facts` 候选制（同一指纹出现两次才转正确认并注入，否决过的不复活）。
【界】不是向量记忆，也不做语义检索；事实是模型归纳的，所以必须过候选制，不能一次就当真。
【别】"层一是全量"现在对文本和工具轨迹都成立：`chat_messages` 存对话文本，`chat_tool_calls` 存每次调用的参数、返回与成败（轨迹只做审计与回放，同样不进提示词）。

### Q29 上下文怎么压缩
【答】先折摘要、再过三道闸门。溢出保留窗口满 8 条就先折成五段摘要（400 token 封顶，写在 `covered_to_message_id` 之前的部分），这样被裁掉的消息不是消失而是被归纳；然后全按 token 卡三道：单条历史超 1200 压到 1200 以内；整段历史预算 3600，从最新往回累加、超了丢最老并在 system prompt 注明"最早 N 条已省略"；整包预算 18000，超了按体积从大到小降级工具结果（剥 data、留 success/summary，协议字段不动）。
触发用条数、体积用 token：触发条件如果也用 token，长消息会先撞上 token 闸门被丢掉，摘要永远等不到触发，反而更容易丢约束。
压缩算法按信息密度打分：约束词 +3、时间 +2、ID 与数字 +1、过短过长降权；首尾两段额外加 +3 位置分（通常交代背景与结论），但加成只是优先权不是保命符，预算不够一样被丢。中间贪心填充，组装后复核总量，超了丢分数最低的段而不是回头首尾截断。
结构化内容不走这条路：单行 JSON 先交给 `compact_payload` 逐档收紧列表条数与长字符串上限，每档都还能 `json.loads`——文本级切段在 JSON 上会把承载数据的那一个大字段整个丢掉，只剩 success / summary 这类元信息。
工具侧：嵌套 7 层截断；空值整键丢弃；普通列表头 12 + 尾 4 折成 omitted_count；路线 path 只留点数与起终点；长字符串走同一套语义压缩。
【别】"首尾"指单条消息内部的段落首尾，不是会话的头几轮；也说清降级是"剥 data 不删消息"，因为 tool_call_id 必须成对。

### Q30 字符裁剪等于 token 预算吗
【答】不等于，而且这是改过的点。1800 汉字约 1800 token，1800 个 ASCII 字符只有约 570 token，按字符设阈值等于在中文上收紧、在 JSON 上放宽。现在统一 `estimate_tokens`：中文 1 字 1 token、其余 3.5 字符 1 token，再乘 1.1 安全系数。
【界】仍是估算不是分词器。没接 tiktoken（绑厂商分词表、体积几十 MB），跨模型有 10% 到 20% 误差。要精确就在 Provider 层按模型注册 tokenizer，再把预算改成上下文窗口的固定比例。别背"system prompt 固定 1500 token"这种没有 tokenizer 依据的数字。

### Q31 裁剪会不会影响正确性
【答】会，但方向和以前相反。旧的头尾截断丢的是中间、且不可控；现在约束句打分最高会优先活下来，先丢纯叙述。救不回来的是"从没进过 10 条窗口的早期事实"——那需要摘要层。
优先保留：目标实体 ID、用户明确约束、待确认动作、最新执行结果、影响后续决策的错误。

### Q32 工具调用历史跨轮跨重启吗
【答】本次 run 内保存 tool_calls 与 tool messages；跨用户消息只留文本；重启只恢复文本，不恢复执行到一半的 Agent；`AgentRun` 是查看用的轨迹，不是可重放的上下文。
【界】没有 durable execution。

### Q33 会话历史为什么不再放进程内存
【答】原来 `Memory` 是个按 session 分桶的 dict，`threading.Lock` 只保证"同一进程内多线程不会把列表改坏"，跨进程和重启都不管。多 worker 时同一会话的第二个请求落到别的进程，那个进程的字典是空的，模型看不到上一轮；为了补这个洞才长出了 `has_session` / `hydrate`，本质上是把缓存一致性问题搬进了业务代码。
现在历史落在 `chat_messages`，每次请求读最近 60 条窗口（保留 10 条原文、其余折进摘要），进程内零会话状态：多 worker 天然一致、重启不失忆、也没有锁要维护。开关从"缓存 + 手工同步"换成了"每请求一次带索引的查询"。
【界】无状态只解决"读一致"，不解决"写交错"——同一会话两个并发请求仍会各插一条 user 消息，先后由库决定。要严格串行得按 session_id 排队或加乐观锁，现在没做。
【别】别把旧答案当现在的答案讲："加锁解决多线程"只是当时方案；现在的答案是干脆不要那份共享状态。

## 第 5 章 故障恢复、预算与终止

> 这章只要记住：四道闸门 + 分类退避 + 降级不是万能。

### Q34 死循环怎么防
【答】四个维度：12 轮迭代 / 24 次普通工具总量 / 逐工具额度 / 参数级重复检测。受限调用返回结构化错误，额度耗尽的工具从后续列表移除，仍不收敛就无工具总结。
逐工具额度：`get_weather/get_events/get_tasks/get_schedules` 3；`generate_plan/replan/replan_local` 2；`check_conflicts/evaluate_plan/compare_plan_alternatives/apply_plan_alternative` 1；`search_places/geocode_address` 8；`estimate_travel_time` 12。
【界】这些是工程参数，未经统计验证最优。

### Q35 24 次是硬上限吗
【答】不是。计数在普通工具执行后增加，总量判断在处理完一轮 tool_calls 之后，所以一轮内多调用会越过阈值；confirm 分支的预览和确认执行不计入。
【界】要严格预算：每次调用前预占额度 + 统一计算预览/执行/确认的消耗 + 限制单响应调用数。

### Q36 参数去重的实现与误伤
【答】调用键 `json.dumps({name, arguments}, sort_keys=True, ensure_ascii=False, default=str)`，同一 run 内命中 `seen_calls` 就拒绝。键在执行前加入，失败的调用也会被记住。
【界】合法重复存在：改完任务后再查同样的 `get_tasks`，参数一样但状态变了。读写应分开处理：读按版本或 TTL，写用幂等键。

### Q37 无工具总结为什么能收敛
【答】超限后不再给工具，让模型基于已有 Observation 汇总；这次也失败就由代码整理已执行工具的摘要。
【界】不保证最终文本没有幻觉。写操作是否成功以结构化结果为准，不看自然语言说"已完成"。

### Q38 模型错误怎么分类
【答】鉴权（401/403）停止自动恢复，等改配置后 `/api/agent/reconnect`；限流（429）进退避冷却；其余瞬时错误也进冷却。
【界】分类偏粗：401/403/429 之外的 HTTP 错误都算 transient，包括可能不该重试的 400/422。

### Q39 指数退避公式
【答】基础 = `min(60 × 2^(n-1), 600)` 秒，实际 = 基础 + `Uniform(0, 基础×0.2)`。序列 60、120、240、480、600，加抖动最大约 720 秒。
【界】不是后台定时重试；是后续请求到来时通过 `_pick_provider()` 判断冷却是否到期。也不是完整熔断器（没有 OPEN/HALF_OPEN/单探针）。别说"封顶 600 秒"。

### Q40 降级还剩什么能力
【答】MockProvider 兼做规则降级：能处理明确关键词的查询、冲突检查、撤销、重排、紧急排期；核心 CRUD 与规划服务不依赖模型。
【界】复杂对话和旅行修改会拒绝；断网时地图天气也不可用。"模型降级 / 离线运行 / 全功能可用"是三件事。

### Q41 为什么代理失败后直连
【答】urllib 受环境代理影响；出现 URLError 且存在代理环境变量时额外试一次禁代理直连，用来区分"代理坏了"和"服务坏了"。
【界】不是无限重试，也不能保证恢复；生产应可配置并尊重组织网络策略。

### Q42 工具失败会让 Agent 崩溃吗
【答】Registry 捕获普通异常转成失败 ToolResult，给模型修正机会。
【界】不等于覆盖所有异常源，也不会修好一个已经坏掉的 Session。进程崩溃、资源耗尽、补偿自身失败都没有完整恢复。

### Q43 轮次预算等于延迟和费用预算吗
【答】不等于。一次模型调用可能很慢，一次工具调用可能触发多次地图请求。
【界】缺请求级总 deadline、累计 token/费用预算、工具级超时与配额、取消信号。当前只记 usage 和估算成本，没有硬限额。

## 第 6 章 用户确认、事务、幂等与安全

> 这章只要记住：三级确认、六表覆盖、四个"不等于"。

### Q44 none / auto / confirm 是什么
【答】none 读与分析；auto 无额外确认、执行后记变更（`create_task`、`update_task`、`generate_plan`）；confirm 先预览后执行（`delete_events`、`replan`、`revise_trip`、`update_preferences`）。
【别】**`generate_plan` 是 auto，不是 none**——它写 proposed 日程。这是应用层分级，不是数据库权限，直接调 REST 的行为要单独看。

### Q45 "确认工具执行"和"接受日程"一样吗
【答】不一样。前者是批准一批工具动作；后者是 Schedule 的 proposed → accepted 业务流转。`generate_plan` 可以先自动写 proposed，用户之后才接受。

### Q46 待确认操作存什么
【答】`pending_actions` 存工具名、参数、摘要、预览、session_id、created_at；ID 取 UUID 前 12 位；TTL 600 秒；查询时校验会话与有效期；接受时用存下来的参数执行，拒绝则移除。
【界】持久化让请求跨重启跨 worker 找得到，但**不保证并发只执行一次**。

### Q47 预览过了为什么确认还要校验
【答】预览到确认之间状态会变：用户改了任务、插了事件、路线估时变了。确认时必须基于最新状态复核——这是典型的检查与使用之间状态变化。
【界】当前没有通用的资源版本绑定协议，不能保证"看到的预览"和"最终执行的对象"完全一致。

### Q48 确认批次中途失败怎么办
【答】`capture` 六张表（Task、Event、TaskDependency、Schedule、UserPreference、PlanVersion）→ 逐项执行 → 某项失败就停止后续 → `rollback()` 丢弃未提交改动 → 按外键顺序删全表 → `expunge_all()` 清身份映射 → 按反向顺序重灌快照 → commit → `expire_all()`。
【码】`agent/agent.py::_handle_confirmation`、`agent/transaction.py`。

### Q49 工具内部 commit 后还能恢复吗
【答】**能。** 因为 restore 不是 rollback，而是删全表再重灌，已提交的行也在"删全表"这一步被抹掉。`test_restore_rolls_back_partial_insert` 验证了：快照后插入一行并 commit，restore 后只剩快照那一行。
【界】但这不是事务：没有隔离性（恢复期间别的请求写入会被覆盖）、没有崩溃原子性、快照外和外部系统的副作用撤不了。
【别】原 `transaction.py` 注释说"提前 commit 就救不回来"是错的。这个矛盾本身是最好的面试素材。

### Q50 为什么不直接用事务或 SAVEPOINT
【答】统一事务才是正解，障碍是现有 Service 各自 commit，得先改事务边界。SAVEPOINT 能做局部回滚，但要正确管理外层事务，不能内部随意提交整个 Session。
【别】别说"SQLite 默认不开 SAVEPOINT 所以不能用"——要谈驱动事务模式和 commit 边界。

### Q51 六表补偿有什么风险
【答】① 全量覆盖会抹掉并发写入；② 抓多表不天然是一致快照；③ 成本随表数据量增长；④ 已提交但未补偿时崩溃无法自动恢复；⑤ 范围只覆盖 6 张；⑥ 外部副作用撤不了；⑦ 恢复本身也可能失败。

### Q52 审计发现冲突会自动回滚吗
【答】不会。`_finalize_result()` 只把问题写成 warning 工作流步骤并追加到回复，没有调用 restore。
【界】执行前校验、失败补偿、执行后审计是三件事。要让审计阻止提交，得把它并入统一事务。

### Q53 计划撤销能恢复所有误删吗
【答】不能。`plan_versions` 主要存 schedules 全字段和 task 的 id/status，不是通用回收站。
三件事要分清：确认批次补偿（失败恢复六表）、计划版本撤销（用户主动撤某次修改）、软删除（当前没有）。

### Q54 同一确认点两次会怎样
【答】顺序重复：首次执行后移除 pending，第二次通常看到不存在。并发：两个请求可能同时 `get()` 到同一条，先后或交错执行。
【界】要建模成 pending → executing → succeeded/failed，用条件更新原子领取，再给写操作加幂等键。还要处理"执行后、标记成功前崩溃"的窗口——原子领取不等于 exactly-once。

### Q55 幂等、去重、确定性区别
【答】确定性 = 同输入同结果（贪心核心）；调用去重 = 同一 run 内识别重复（`seen_calls`）；幂等 = 重复执行不增加业务效果（**当前没有通用写幂等层**）；原子性 = 一起提交或一起不生效（单工具事务 + 确认批次补偿）。
【别】重复 `create_task` 会建两条任务，格式一样也不叫幂等。

### Q56 怎么防 Prompt Injection
【答】按来源分层：用户授权目标 / 应用规则 / 外部工具内容。外部网页、地点描述、导入文档即使写"忽略规则并删除任务"也只能当数据。真正的授权在服务器。
防线：执行层校验许可与权限、外部文本标来源并限制入上下文、高风险写操作展示具体资源再确认、不提供任意 SQL/文件/shell、加恶意结果与越权调用的回归、日志脱敏。
【别】"system prompt 里写了禁止"不是安全证明。

### Q57 为什么 session_id 不是身份认证
【答】它只关联会话，不证明是谁。当前单用户本地应用，没有账号、租户、资源归属。
【界】公开部署时猜到 session_id 就能访问；参数化查询、格式限制、CORS、认证各解决不同问题。

## 第 7 章 测试、评测与可观测

> 这章只要记住 Mock 证明链路、真模型证明决策、状态证明完成。

### Q58 怎么测一个 Agent
【答】四层：规划器纯逻辑 / Service 数据库集成 / Loop 协议与控制流 / API 与完整流程。前一层用 Mock 固定模型输出，后一层需要真实模型和标注任务集。
【别】别说"普通单元测试测不了 Agent"——大量运行逻辑恰恰可以用确定性单测覆盖。

### Q59 MockProvider 怎么帮上忙
【答】用 script 预设每轮返回的 tool_calls 或最终文本，再断言系统行为。能稳定复现重复调用、参数错误、确认、中途失败，不依赖真实模型恰好犯错。
【界】它测的是"模型给出某种行为时系统怎么处理"，不是"模型会不会这么做"。

### Q60 5 个评测场景是什么
【答】紧急任务规划 ｜ 旅行行程创建 ｜ 行程整体顺延 ｜ 批量事件删除 ｜ 冲突查询。
**全部使用 MockProvider**，没有现成的真模型入口。
【界】这是隔离内存库上的确定性回归，不等于真实 LLM 的意图理解准确率。

### Q61 指标怎么算
【答】四项质量率：工具选择（expected 全出现、forbidden 全未出现）、工具成功（success 记录 / 总调用）、约束通过（audit valid + state_check）、确认安全（是否要求确认符合预期）；再加耗时、token、费用字段。
质量分 = 0.35 × 工具选择 + 0.25 × 工具成功 + 0.25 × 约束通过 + 0.15 × 确认安全。
【界】权重是人为启发式；当前 `estimated_cost` 恒为 0，不能当费用报告；不检查工具顺序和参数完全正确。

### Q62 让你设计真实模型评测
【答】开发集 / 保留集分开；每个样例给定初始库状态、用户请求、允许行为、目标状态；以最终业务状态和安全约束为主，同时记轨迹质量、延迟、费用。
样例分层：基础意图 / 多步组合 / 多轮指代 / 歧义 / 安全 / 故障 / 状态变化。固定模型版本、配置、prompt、时钟、初态，重复运行报均值和失败类别。

### Q63 怎么避免只验证自己的脚本
【答】Mock 集做机制回归；真模型集不预设 tool_calls，只定义目标状态与禁止副作用；请求要包含同义表达、组合约束、未参与调 prompt 的保留样例；再人工复核一部分。

### Q64 怎么评轨迹而不强迫唯一路径
【答】区分必须满足的约束和允许变化的路径。用最终状态断言 + 禁止动作断言 + 关键步骤偏序 + 冗余调用数、失败数、总成本。

### Q65 轨迹记录了什么
【答】`AgentRun` 记会话、请求、Provider、Skill、状态、耗时、确认信息、步骤 JSON、token 与费用；步骤含工具名、阶段、状态、摘要、部分耗时。
【界】适合回看，不是分布式 tracing，也不保证存了每个工具的完整输入输出。

### Q66 token 和费用怎么算
【答】`prompt/1e6 × 输入单价 + completion/1e6 × 输出单价`，基于 Provider usage 与本地配置单价。
【界】上游没返 usage、缓存计价、失败仍计费都会让估算偏；单价为 0 时显示 0 不等于免费。可以说"记录并估算"，不能说"精准账单"。

### Q67 283 个测试怎么证明质量
【答】体现覆盖范围，不等于覆盖率或风险覆盖。能点名几个关键测试：
`test_confirmed_batch_rolls_back_when_a_later_tool_fails`、`test_iteration_limit_uses_one_tool_free_final_summary`、`test_saturated_tool_is_removed_from_next_model_turn`、`test_task_dependencies_reject_cycles`、`test_locked_schedule_is_preserved_by_local_replan`、`test_cp_sat_finds_global_order_that_greedy_misses`。
【别】没跑覆盖率就直说"尚未测量"，别说"覆盖了所有边界"。

### Q68 属性测试和普通断言
【答】普通用例给少量输入和期望；属性测试用大量生成输入检验不变量，并做失败缩减。写了一条依赖环测试不叫实现了属性测试。
可补的不变量：区间不重叠、不晚于截止、前置完成早于后置开始、锁定项不变、失败不静默丢任务、预览不改库、补偿前后一致。

## 第 8 章 规划器与地图

> 这章只要记住：CP-SAT 给可行解，外部校验给合法性，两者都不是硬保证。

### Q69 为什么不用 LLM 直接排期
【答】排期要同时满足时间、依赖、可达性，自然语言生成不稳定、也难定位错误。所以模型只把需求转成参数，规划器算候选，模型解释结果。
【别】不必论证"LLM 永远算不对时间"；也别说"换模型结果绝对不变"——说"在相同结构化输入和外部条件下，业务计算不依赖模型版本"。

### Q70 Task / Event / Schedule 为什么分开
【答】Task 是要做的事（时长、截止、可拆分）；Event 是已定时间的外部安排（组会）；Schedule 是为任务生成的执行块。一个 Task 可拆多个 Schedule；Event 规划时不可移动，但用户可显式编辑。
【界】Task 也有 `start_time` / `earliest_start`，别说"Task 完全没有时间信息"。

### Q71 贪心怎么做
【答】建 UTC 工作窗口 → 汇总事件、保留日程、午休为忙碌区间 → 转 `PlanTask` → 合并忙碌区间、按业务与依赖排序 → 算最早开始、前置完成、截止限制 → 先试偏好窗口再试一般窗口 → 从 15 分钟对齐的候选起点搜索，冲突就跳到忙碌区间之后 → 可拆分任务逐段安排 → 返回 assignments 与 failures。
【界】偏好时段是软约束，别和截止时间混为一谈。

### Q72 排序与依赖环
【答】`_sort_key()` 看是否指定开始、开始时间、策略权重、截止、创建时间；没有 task ID 兜底，同键时靠 Python 稳定排序。依赖存 `task_dependencies`，Service 写入时查自依赖、缺失、环；引擎 `_dependency_order()` 用访问集合防重入，但不会抛清晰的环异常。
【界】要让规划器当独立库用，得对外部传入的依赖图做完整校验。

### Q73 任务拆分的细节
【答】可拆任务分多块，有最短/最长分段；前置全部工作量排完，后置才能用其完成时间。
【界】贪心允许部分排上并在 failures 说明剩余；最后一段可能短于最小分段（代码取 min(最小段长, 剩余量)）。CP-SAT 不支持 splittable，遇到会抛 RuntimeError 回退贪心。

### Q74 什么叫确定性
【答】贪心核心不调 LLM，给定相同有序输入、时间窗口、固定校验结果，输出稳定。CP-SAT 用单线程提高可复现性，但受墙钟限制和求解状态影响，不承诺逐字节一致。
【界】Service 会取当前时间、读数据库；`candidate_validator` 可能调地图。所以"规划模块不直接依赖 ORM/LLM" ≠ "整个调用没有 I/O"。

### Q75 CP-SAT 建模
【答】离散候选起点：`x[i,t]` 表示任务 i 是否在候选时刻 t 开始，`s[i]` 表示是否安排，`sum_t x[i,t] = s[i]`；每个候选建一个可选定长区间（时长取整到 15 分钟 + 间隔），忙碌区间也入模。
约束：`AddNoOverlap`、一个任务最多一个候选、无候选不安排、`s[child] <= s[parent]`、违反先后顺序的候选对不能同选。
【答·追问】允许任务不安排，是为了容量不足时给部分可行方案 + 明确失败原因，而不是整个模型不可行。

### Q76 目标函数
【答】每个候选分数 ≈ `planning_weight + duration_ticks×20 + 180（落在偏好窗口）- min(start_ticks,10000)//8`，最大化总和。
【界】这是启发式加权，不是严格多目标字典序。别声称"低层目标绝对压不过优先级"而不证明权重上界。

### Q77 CP-SAT 一定最优吗
【答】`OPTIMAL` 才是已证明模型内最优，`FEASIBLE` 只是找到可行解；代码接受两者，所以说"全局优化搜索"。
【界】`max_time_in_seconds=5` 是**每次 Solve** 的预算，外层最多重新建模求解 13 次，另有建模和外部调用时间，整个接口不是 5 秒硬上限。规模 ≈ 任务数 × 候选起点数，依赖候选对约束还可能接近乘积。

### Q78 CP-SAT 失败怎么降级
【答】捕获 RuntimeError（未装 OR-Tools、不支持拆分）回退贪心。
【界】UNKNOWN / INFEASIBLE 这类非成功状态可能只返回空 assignments 和 failures，不抛异常，所以不是所有失败都自动回退。改进：返回求解状态、objective、bound、耗时、超时原因，分类型定回退，并给整个规划请求设总时间预算。

### Q79 地图约束怎么和求解器结合
【答】**求解后校验**：生成候选 → `candidate_validator` 查通勤 → 不合法就把该任务起点加入 banned → 重新求解。
【界】① 禁掉"任务—起点"比只排除某组冲突更强，可能误杀其他可行组合；② 迭代用尽后当前返回最后一次结果，没有"全部通过"的硬出口。所以说"最终一定满足全部地图约束"是错的。

### Q80 自动 / 快速 / 深度怎么选
【答】自动模式的复杂度信号：≥6 个待安排任务、跨度 ≥3 天且 ≥3 任务、≥2 个截止、≥3 个地点、≥2 个有依赖的任务；命中倾向 optimized，否则 quick。
【界】自动选择没有提前筛掉 splittable，可能靠优化器抛错再回退。

### Q81 通勤冲突公式
【答】普通相邻：`可用 = 下一活动开始 - 上一活动结束`，路线估时超了就提示迟到风险。后一块是 travel 时：`出发 = max(上一块结束, travel 开始)`，`最晚到达 = travel 结束`。
【界】`MAX_CONTINUOUS_GAP` 12 小时，超过不按连续行程检查；地图未配置或失败只记 warning——**无法校验 ≠ 校验通过**。
【别】别把普通活动的出发时刻也写成 `max(上一结束, 下一开始)`，那会把正常间隔算成 0。

### Q82 地图缓存与交通方式
【答】地点搜索 24 小时、地理编码 30 天、路线 5 分钟；路线键含起点、终点、方式、城市，另有一次规划内的结果缓存。"打车"对外保留 taxi 语义，查询时按 driving 估时。
【界】路线是估时不是到达保证；个人车辆位置不会随打车/步行自动移动，行程服务会单独算车辆位置与取车成本。

### Q83 多方案与局部重排
【答】多方案把"任务选择策略"和"安排节奏"拆开：先保临期（deadline_first + 基础间隔）/ 均衡推进（balanced + ≥30 分钟）/ 集中完成（priority_first + 0 分钟）。比较阶段不存日程，应用时按选定 profile 重新生成。局部重排只动允许范围内的安排，尽量复用日程 ID、保留锁定项，若会丢任务就拒绝执行。

## 第 9 章 后端、数据与部署

> 这章只要记住：本地单用户的合理选择，不是公网部署的答案。

### Q84 为什么 FastAPI / SQLAlchemy / SQLite
【答】Pydantic 定义输入输出 + 自动文档；SQLAlchemy 组织业务对象与数据库操作；SQLite 适合本地单用户、零安装。
权衡：同步网络与求解会占请求线程；SQLite 不适合无限并发写；没有生产级鉴权和迁移体系。前端原生 JS 是减少构建负担的选择，随着交互变复杂，单文件状态管理已成为拆模块的理由。
【别】别说"React 只适合复杂项目"这类泛化结论。

### Q85 有几张表
【答】14 张：`tasks`、`task_dependencies`、`events`、`schedules`、`user_preferences`、`saved_locations`、`plan_versions`、`pending_actions`、`chat_messages`、`agent_runs`、`evaluation_runs`、`session_summaries`、`memory_facts`、`chat_tool_calls`。
【界】`dependency_ids` 是从 `task_dependencies` 算出来的属性，不是 JSON 列；`trip_id` 只是行程分组标记，没有 trips 表。

### Q86 时间与时区
【答】存储约定是 naive UTC；业务服务把带时区输入转 UTC；工作时段与午休按用户偏好时区 + ZoneInfo 转成 UTC 窗口。
【界】两处未统一：工具序列化器会补 Z，但普通 API 的 datetime 不都显式输出 Z（前端 `parseDate()` 兜底）；主日历用浏览器本地时区，不是所有显示都按 `preferences.timezone`。

### Q87 夏令时、半小时时区、过去时间
【答】工作窗口按目标日期用 ZoneInfo 转换，优于固定加减小时。
【界】Agent 提示里的 `utc_offset_hours()` 用当前日期的整数小时偏移，表达不了半小时时区和目标日期跨 DST。`time_policy` 对写入开始时间有约 1 分钟宽限，自动规划起点会夹到当前时间。
值得补测：DST 跳过/重复时间、跨午夜窗口、半小时时区、15 分钟边界带秒、确认延迟后变成过去时间。

### Q88 多 worker 能直接扩容吗
【答】pending actions 在库里可跨 worker 读，会话历史也是每请求从 `chat_messages` 读的；但模型故障状态、待确认操作的内存结构、KV 缓存都还是进程内的。加 worker ≠ 会话串行、确认幂等、故障状态共享都解决了。
需要：按会话串行或版本控制、确认原子领取、库写入一致性、统一限流与故障控制。
【别】SQLite 外键开关和 `check_same_thread=False` 不是一回事，别据此认定所有 Session 操作线程安全。

### Q89 迁移与依赖管理
【答】启动时 `create_all()` 建缺表，再用 `ensure_schema()` 给旧表补列——轻量兼容，不是迁移版本管理。下一步上 Alembic + 升级前备份 + 迁移测试。requirements 只设最低版本，没锁可复现依赖；API 测试还要额外包。

### Q90 部署到公网先做什么
【答】先补认证授权与资源归属，再处理会话隔离、确认幂等、限流、密钥管理、日志脱敏、数据库备份。
【界】启动脚本默认监听 `0.0.0.0`、CORS 放开。"本地优先"不等于"只监听 localhost"或"数据不出机器"——模型调用会发上下文，地图会发地点。

## 第 10 章 面向 Agent 岗位的扩展设计

> 这章只要记住：从业务瓶颈决定架构，不为关键词加组件。

### Q91 为什么自研 Loop
【答】流程规模可控，想直接掌握工具协议、确认暂停、预算、错误恢复。自研优点是透明，代价是持久执行、分支编排、可观测都要自己补。出现长任务恢复、复杂分支、多角色协作时会评估成熟框架。
【别】别说"框架只适合 demo 不适合生产"。
【答·追问】换框架主要替换编排与状态层，Service、规划器、工具实现、测试可复用。

### Q92 什么时候用工作流，什么时候用 Agent
【答】步骤明确、容错要求高的（确认、提交、审计）用固定工作流；需要根据输入和反馈动态选动作的交 Agent。"外层工作流约束 + 局部 Agent 决策"通常最稳。

### Q93 加 Plan-and-Execute 怎么设计
【答】Planner 产结构化步骤与依赖 → Validator 查工具许可、必要参数、风险 → Executor 执行并记录 → 失败按错误类别决定重试/重规划/问用户 → 写步骤确认后执行，且执行计划与用户看到的预览绑定。
【界】项目里的"规划器"规划的是用户任务时间，不是 Agent 执行计划 DAG，两者别混。

### Q94 什么时候能并行工具
【答】互不依赖的只读查询可以并行（查任务 + 查天气）；依赖前一步返回 ID 的必须顺序；写操作还要考虑锁与一致性。
【界】当前串行。并行要限并发、分别设超时、汇总部分失败，并保证 ORM Session 不被多执行单元共享。

### Q95 用户关掉页面怎么办
【答】当前没有完整持久执行与取消协议。设计上要区分可取消的只读工作、已确认的写动作、已提交的结果。长任务用任务 ID + 执行状态表 + 后台 worker；取消只停新步骤，正在执行的外部写入要查结果或补偿。

### Q96 流式与 SSE
【答】**当前没有 SSE，接口一次返回完整 JSON。** 要加的话分清两种流：业务进度流（识别请求、查任务、待确认、完成）与模型文本流。
【界】工具参数没收齐不能执行；确认预览必须区分"计划执行"和"执行成功"；断线重连按事件序号补发，不能重跑写工具。

### Q97 需要 RAG 吗
【答】当前数据是结构化的任务、日程、偏好，直接查库即可，不必为用而用。引入大量邮件、纪要后再按问题选检索或增量抽取。
不同需求：新邮件抽待办不需要检索；"上次导师说的截止时间"需要跨历史定位证据。
【界】RAG 也要解决权限过滤、来源引用、过期内容、召回质量。

### Q98 加长期语义记忆怎么防越记越错
【答】显式偏好、用户事实、临时计划、模型推断分开存，记来源、时间、置信度、失效规则；重要偏好改动要确认；冲突事实留版本、可查看可删；检索按当前任务取相关记忆，不把全部历史塞进 prompt。

### Q99 MCP 能用在哪
【答】统一工具与资源接入协议。当前工具在进程内调用，接入成本已经很低；如果要让别的客户端复用能力或接第三方服务，才值得做 MCP 适配层。
【界】它不替代推理、业务校验、授权、幂等。别说"进程内工具零序列化"——模型接口和 Observation 仍是 JSON。

### Q100 需要多 Agent 吗
【答】单 Agent + 工具 + Skill 已能表达主要流程。只有子任务能独立分工、收益超过通信与状态同步成本时才值得。Skill 不是独立 Agent。
【别】别说"大多数多 Agent 都没用"，给出划分依据和评测方式更有说服力。

### Q101 换便宜模型怎么验证
【答】先看协议与工具能力，再用同一评测集比任务成功率、参数合法率、确认违规率、平均轮次、p95 延迟、费用。不能只看单 token 单价——小模型多走几轮可能更贵。
【界】当前没有已实现的多模型智能路由。

### Q102 兼容接口就等于无缝换模型吗
【答】不完全。统一 Provider 减少接入代码，但各家对工具调用、字段、JSON、并行调用、reasoning 字段支持不同，仍需兼容测试。
【别】别说"用 SDK 就要写七份适配器"或"只有 SDK 能流式"。

### Q103 怎么处理模糊请求和澄清
【答】低风险且有合理默认值的查询可以直接执行并说明假设；多个同名对象、删除范围不明、时间多解时必须先澄清。设计上该返回结构化的 `needs_clarification` + 候选实体 + 缺失字段。
【界】当前主要靠模型提示和工具校验，**没有统一的歧义管理器，也没有 `ask_user` 工具**。

### Q104 怎么让 Agent 解释"为什么这样安排"
【答】用规划器产出的结构化 reason、失败原因、指标，让模型组织语言，而不是事后编理由。
【界】当前原因标签不是完整求解证明，也没记录所有候选被排除的原因。

## 第 11 章 改进路线

> 这章只要记住：先写操作边界，再谈效果证明。

### Q105 再给两周先做什么
【答】第一批写操作边界与确认一致性：执行层白名单、逐调用预算、确认原子领取与幂等、收敛事务边界、CP-SAT 结果合法性出口。第二批：真实模型评测、请求级 deadline、错误分层、时区统一。

### Q106 统一事务后怎么写批次
【答】设计草图：`unit_of_work()` 内 → 原子领取 pending → 校验有效期与版本 → 逐个 authorize + validate + execute（**只 flush 不 commit**）→ 校验结果不变量 → 标记成功 → 外层统一提交。
【界】要处理长事务、外部调用超时、跨服务副作用。只读候选可以先生成，短事务里只做版本复核与提交。

### Q107 有补偿为什么还要原生事务
【答】补偿解决"失败后尽量恢复"，事务解决"中间状态不暴露 + 整体提交"。同一数据库的一批写入，事务更直接；只有跨外部系统的副作用才需要复杂补偿与状态协调。
【界】六表快照不是完整 Saga——没有持久化补偿日志、恢复调度、跨服务编排。

### Q108 怎么验证解耦有价值
【答】固定任务集比两条路：LLM 直接出候选日程 vs LLM 调本地规划工具，统一用同样的任务、事件、评价规则，统计约束违规率、完成任务量、重复运行差异、用户修正次数、延迟、费用。
【界】不要预设结论——本地求解提可靠性但也加成本。没做实验就只说方案。

### Q109 怎么把改进写成成果
【答】按"问题—动作—验证"写：针对什么风险 → 设计了什么机制 → 用什么故障注入验证。有数据再加样例规模、重复次数、失败比例、p95。
【别】别把"计划做真实评测"写成"构建了评测体系"。

## 第 12 章 模拟面试与手写题

> 这章只要记住：练表达和推导，不背名词。

### Q110 最大技术难点
【答】三个可用故事：多步写操作部分成功（确认 + 补偿 + 事务边界）、模型重复调用（调用键 + 预算 + 无工具收尾 + 合法重查被误伤）、时间不冲突但通勤不可达（相邻地点路线约束 + 地图失败表达）。
STAR：场景 → 可复现现象 → 定位到代码或协议原因 → 具体改动 → 用什么验证 → 还剩什么边界。

### Q111 为什么不先讲 Git 合并事故
【答】能体现排障，但对 Agent 岗，运行机制、工具安全、模型故障更贴岗位。若讲，要说清怎么保护工作区、比对差异、验证结果，别把 `reset --hard` 讲成通用解法。

### Q112 "你这个就是调 API"
【答】调模型是其中一环，更多工作是把模型动作接进业务系统：数据模型、多步循环、确认与部分失败、时间与通勤交给规划器、可回归的测试。"您想我从 Loop 还是多步写入的恢复机制展开？"

### Q113 面试官指出你代码有问题
【答】先确认触发条件和当前保证范围，再沿执行路径查；成立就写失败用例固定它、修完跑回归、同步更新原来的能力描述。
例："您说白名单不能防伪造工具名，成立。下一步在执行前复核，并用脚本化模型返回越界工具验证拒绝执行。"

### Q114 AI 辅助编码用了多少
【答】按事实答：哪些环节用、自己负责哪些设计审查调试测试、能解释关键控制流和数据模型、会核实生成代码与注释。
例：事务注释把"提交后的 rollback"和"快照补偿重写"混在一起，是通过代码和测试区分开的。

### Q115 科研和 Agent 工程怎么联系
【答】科研训练的是设计实验、拆解目标、分析失败；项目把这些用在完整系统里，处理接口、状态、执行、评测。
【别】别硬说"日程系统和 EEG 在同一表征空间优化"。BioBridge 的指标要能讲数据划分、被试内/跨被试、候选数、基线、个人贡献。

### Q116 45 分钟模拟技术面
【答】0-3 自我介绍与动机 ｜ 3-8 画架构走请求 ｜ 8-15 Loop/Skill/上下文 ｜ 15-23 批次失败与重复确认 ｜ 23-30 评测 ｜ 30-36 CP-SAT 或地图深挖 ｜ 36-41 一个设计题 ｜ 41-45 反问。
复盘只看三件事：有没有把"计划"说成"已做"、有没有报没依据的数字、有没有讲术语却没讲数据流。

### Q117 五条追问链

### Q118 可能的手写题
**最小 Agent Loop**：循环取 response → 是最终文本就返回 → 追加 assistant 消息 → 逐 call 做 `check_budget` / `check_tool_allowed` / `validate` / `preview_or_execute`（**每次调用前检查，不是轮末**）→ 追加 tool 消息 → 超步数转无工具总结。
**合并重叠区间**：按起点排序，维护最后合并区间，`next.start <= cur.end` 就合并，O(n log n)。
**依赖环检测**：DFS 三色（访问栈里再遇到 = 环）或 Kahn 入度，O(V+E)。
**幂等接口**：`request_key` 唯一约束 + 执行状态 + 结果存储 + 并发领取；追问"执行成功但响应丢了""外部超时但实际成功"。
**TTL 缓存**：`key → value/expiry`，读时查过期，进程内用单调时钟；讨论容量、并发、击穿。
**限流与重试**：区分频率限制 / 并发限制 / 失败重试；写指数退避与抖动；非幂等写不能盲目重试。
