## 〇、开场前必须先纠正的三处

### ★★★ 0.1 “本地优先”到底指什么（不纠正，第 1 题就会被打断）

默认配置里 LLM 走的是远端 API。说“本地优先”而不解释，面试官一句“任务内容不还是发给 OpenAI 了”就能问住。

准确说法（背下来）：

> 本地优先指的是三件事：**数据落在本地 SQLite、排期计算完全不依赖模型、模型层可以整体换成本地 Ollama 或 vLLM**。默认配云模型只是部署选择——本地模型质量不够，但架构上随时能切回完全离线。

依据：`app/llm/` 是抽象层，`openai_compat` 只是其中一个实现，base_url 可指向 Ollama。

### ★★★ 0.2 就是 ReAct，要说，而且要说准

这个项目的 Agent 层确实就是 ReAct 闭环：推理 → 调工具 → 拿 Observation → 再推理。**不要藏**，主动说。要改的只有两点：拼写和层次。

**拼写：写成 `ReAct`（Reasoning + Acting），不要写成 `React`。** 面试官第一反应会是前端框架 React.js，一句"你说的是前端那个 React 吗"就把节奏打乱。这点只影响书面材料和你自己的笔记，口头说不会歧义。

**层次：被追问"这算 ReAct 吗"时，用这四层回答，比点头强得多。**

```
ReAct            推理与行动交替的组织思路      ← 我用的是这个
Function Calling 模型表达工具名和参数的接口机制  ← 我走的是这个
Agent Runtime    调用、执行、记忆、预算、终止    ← 我实现的是这个
Workflow         开发者预先固定的流程          ← 确认与补偿在这一层
```

> 我是按 ReAct 的"推理—行动—观察"组织闭环的，但动作由模型原生 Function Calling 表达，不是在文本里解析 `Thought/Action/Observation`。区别在于工具调用的格式由协议层保证合法——我不需要写解析器，也不用处理"模型把 JSON 写坏了"这类问题，只在参数语义和业务校验上花功夫。

**这半句是加分点：** 绝大多数人只会说"我用了 ReAct"，能讲清"我用协议层替代了文本解析"才算真懂这个架构。

**顺带一个诚实的边界：** 严格来说文本 ReAct 会把推理过程显式写出来，而 Function Calling 模式下模型不一定输出完整思考链，所以更准确的说法是"ReAct 的组织方式 + Function Calling 的动作表达"，不宣称"完整思维链都可见、都持久化"。

## 一、15 道必背题

### ★★★ 1. 用一分钟介绍你的项目

**【15 秒版】** 我独立做了一个本地优先的日程规划 Agent：LLM 负责理解需求和选工具，本地 CP-SAT 负责算时间，中间用确认和事务兜住写操作。

**完整回答：**

> 我独立开发了 PlanPilot，一个本地优先的智能日程规划 Agent。用户可以自然语言提安排任务、调整行程、检查冲突的要求。我把系统分成两层：LLM 负责理解需求和多步工具决策，本地规划器负责时间、依赖和通勤这些确定性约束。
>
> Agent 层是一个 ReAct 风格的循环，用原生 Function Calling 表达动作——模型返回工具调用就执行、把结构化结果作为 Observation 回传、再进下一轮。注册 37 个工具和 10 个场景 Skill，配了上下文裁剪、调用预算、危险操作确认和模型故障降级。业务侧有 CP-SAT 全局优化、局部重排和计划撤销。目前 270 个测试方法、5 个确定性评测场景和持久化执行轨迹，形成从需求理解到业务执行再到验证的闭环。
>
> 补充一句“本地优先”的准确含义：数据和计算都在本地，模型层可以整体换成本地部署。

**对方最可能接着问：**

1. 你自己做了哪部分？→ 全部。从数据模型、Agent 循环、工具层、规划引擎到前端确认交互和评测，都是我一个人写的。
2. 最难的地方是什么？→ 多步写操作部分成功，见第 11 题。
3. 挑一条链路讲代码。→ “查询论文任务 → 提高优先级 → 生成带 30 分钟间隔的计划”，对应 `loop.py` 主循环 + `planning/engine.py`。

**记忆词：** 业务目标 → 双层架构 → Agent 控制 → 验证。

### ★★★ 2. 为什么要把 LLM 和规划引擎分开？

> 因为“理解用户要什么”和“算出具体排在哪”，是两个不同的问题。
>
> 用户说“论文优先安排，避开组会，任务之间留半小时”。LLM 负责理解这句话：查论文任务、提高优先级、调用规划工具并把间隔设成 30 分钟。规划工具背后的引擎再根据任务时长、截止时间、已有日程和依赖关系，算出每个任务具体落在哪个时间段，排不下的返回原因。
>
> 这样具体排期有明确的计算规则和校验依据，能独立测试；LLM 只负责把自然语言转成操作，并向用户解释结果。

**追问：那 LLM 还有什么用？**

> LLM 负责连接需求和能力。“论文比较急”要拆成查找任务、改优先级、重排三个操作；规划引擎只接受结构化任务和约束，它不理解这句话，也不会自己决定调哪些工具。

**记住这个例子就够了：**

> LLM 把“论文优先、留出休息”转成工具调用；规划引擎算出“论文周二九点开始，下一个任务十点半开始”。

**记忆词：** 软决策交给模型，硬约束交给工具。

### ★★★ 3. 你的 Agent Loop 到底怎么跑？

> 收到消息先做一次关键词先验：命中高置信业务词就带入该场景的指引，没命中就走通用模式。然后组织通用规则、业务状态摘要和最近历史，把**过滤后的**工具清单发给模型——按场景白名单收窄、剔除额度已经耗尽的工具，但场景切换工具永远保留，否则切进收窄场景就再也切不回来。模型认可当前场景就直接调业务工具；不认可就第一轮调 `select_skill` 换掉，换完再继续。返回文本就结束；返回 tool_calls 就校验并逐项**串行**执行，结构化结果作为 Observation 回传。confirm 级调用先预览，同一轮的预览合并成**一次**确认再暂停；到预算阈值转入无工具总结。

```
用户 → 关键词先验 → system + 历史 + 工具清单 → LLM
             ↑                                  │
      select_skill 覆盖                        ├─ 纯文本 → 最终回答
             │                                 └─ tool_calls → 校验 / 预览 / 串行执行
             └──────── Observation 回传 ←──────────────┘
                                       ↓
                              最终回答 / 等待确认
```

**具体例子：** 查询论文任务 → 提高优先级 → 生成留有间隔的计划 → 总结。

**追问怎么接：** 这是 ReAct 闭环——推理 → 工具调用 → Observation → 再推理，动作由原生 Function Calling 表达而不是文本解析（见 §0.2）。同一请求可以多轮调模型，**同轮的多个工具当前是串行处理的**（不是并行）。

**数字：** 12 轮迭代上限、24 次业务工具执行阈值、逐工具额度（`get_weather` / `get_events` / `get_tasks` / `get_schedules` 各 3 次，`generate_plan` / `replan` 各 2 次，`check_conflicts` / `evaluate_plan` / `compare_plan_alternatives` 各 1 次），**场景切换单独限 3 次且不计入这 24 次**。

### ★★ 4. Tool Registry 怎么设计？为什么还要 Service 层？

> 我把 Agent 能执行的操作逐个封装成工具，每个工具说明自己叫什么、能做什么、需要哪些参数、是否需要用户确认。Tool Registry 统一管理：调模型前把工具说明整理给模型，模型返回工具名和参数后，Agent 通过注册表找到对应工具执行，再把成功或失败原因回传。
>
> 工具内部不重复实现业务逻辑，而是调用 Service。比如“创建任务”工具调用任务 Service，由 Service 校验并落库。前端手动创建任务也走这个 Service，两个入口共用一套业务规则。

**用“创建任务”理解：**

```
模型返回：调用 create_task，参数是“写论文，预计 60 分钟”
    ↓
Registry：找到 create_task 对应的工具
    ↓
Tool：整理、校验参数，调用 task_service.create_task()
    ↓
Service：检查业务条件，写入数据库
    ↓
Tool：把结果包装好，返回给 Agent 和模型
```

**追问：为什么不能直接让模型调 Service？**

> Service 是给程序调的，没有模型需要的工具说明、参数 schema 和确认等级。Tool 补齐这些信息，作为模型使用业务能力的入口；Registry 负责统一管理这些入口。

**记忆词：** Registry 找工具，Tool 接模型，Service 办事。

### ★★ 5. Skill 是什么？和 Tool、多 Agent 有什么区别？

> Tool 是可执行能力，Skill 是场景策略，包含关键词、优先级、场景提示和可选的工具白名单。比如旅行规划 Skill 引导模型先查地点和路线、再批量创建行程，而不是走普通任务排期。
>
> 当前是**一个 Agent 用不同 Skill，不是 10 个独立 Agent**。

**追问怎么接：** Skill 是两层：关键词是规则先验，模型自选是兜底和纠错。先验按 priority 比，再比命中词总长度和命中数量；没命中、或者命中了但不是真实意图，模型可以用 `select_skill` 换掉。**路由决策不靠模型猜，但模型有否决权**——这两件事分开，才不会互相污染。当前只有三个 Skill 配了显式白名单，而且主要作用在过滤模型可见 schema 这一层；要做执行硬隔离，还得在 dispatch 前再复核一次。

**记忆词：** Tool 是动作，Skill 是用法，Agent 决定下一步。

### ★★★ 6. Context Memory 具体怎么做？

**【15 秒版】** 记忆分三层：全量流水进表不进提示词；给模型的窗口溢出就先折成五段摘要再按 token 卡预算；跨会话的规则、偏好、事实分区存，事实过候选制才注入。

> 会话历史落在 `chat_messages` 表，按请求读窗口；长期偏好存在 `user_preferences`。发给模型时按 token 分三档管：单条超 1200 token 先压，整段历史预算 3600、超了从最老的丢并在 system prompt 注明省略了多少条，整包 18000、超了按体积从大到小降级工具结果——剥掉 data 只留 success 和 summary，协议字段不动。压缩本身按信息密度打分而不是头尾截断：约束词、时间、ID 加分，首尾段有位置加成但预算不够一样会被丢；单行 JSON 另走结构化路径，逐档收紧列表保留条数，保证压完还能 `json.loads`。工具结果也按嵌套深度、列表长度、字段类型压缩——比如地图路线只留点数和起终点。

**追问怎么接：** 字符裁剪不是精确 token 预算，也可能丢约束。后续应该显式保存目标实体、用户约束和待确认动作；对话文本跨请求是靠表恢复的，但**工具调用的完整轨迹不跨请求**——中间那几轮 tool_calls 只活在本轮 prompt 里，下一轮重新查。

**记忆词：** 会话文本 + 结构化偏好 + 当前状态 + 本轮工具反馈。

### ★★★ 7. 怎么防止死循环和重复调用？

> 我设了 12 轮迭代上限、24 次普通工具执行阈值和逐工具额度，并把工具名加规范化参数生成调用键，拦同一 run 内的重复调用。错误结构化回传，额度耗尽的工具从后续列表移除，最后用无工具总结收尾。

**追问怎么接（这段是重点，别说成“已经解决了”）：**

> 有三个边界我很清楚：第一，总次数是在每轮结束后检查的，所以不是逐次硬上限；第二，参数去重会误伤——用户先查了“明天的日程”，改完任务后确实需要重查同样的条件；第三，它防的是同一 run 内的重复，**跨请求的写操作幂等它管不了**。

**记忆词：** 轮数、总量、单工具、参数去重、最终收尾。

### ★★ 8. 模型挂了怎么办？降级还能做什么？

> 先分类：鉴权失败停止自动尝试，等修配置并重连；限流和瞬时故障进带抖动的指数退避。冷却期间用本地规则 Provider，支持部分查询、冲突检查、撤销和明确的排期请求。核心 CRUD 和规划服务不依赖模型，但复杂语义理解会降级，断网时地图和天气不可用。

**追问怎么接：** 退避基础 60 秒、上限 600 秒，再加 0～20% 随机抖动；**不是后台一直重试**，而是后续请求到来时判断要不要恢复真实模型。

**记忆词：** 分类 → 冷却 → 本地能力 → 受控恢复。

### ★★★ 9. 危险操作怎么确认？批次中途失败怎么办？

**【15 秒版】** 需要确认的操作先展示再执行，多个合并成一次确认；执行前把六张业务表整体快照，中途失败就擦回快照。

> 对删除、重新规划这类需要确认的操作，Agent 不立即执行，而是先展示准备改什么，让用户确认。同一轮多个待确认操作合并展示，用户只点一次。系统和参数一起落库到待确认表，确认后再逐个执行。
>
> 执行前先把六张核心业务表的全部数据序列化成快照。第一步成功、第二步失败，就停止后续操作，用快照恢复——当前事务回滚、全表按依赖顺序重灌，避免留下半完成状态。

**举个例子：**

```
准备执行：删除事件 A、删除事件 B
                  ↓
展示删除清单，等待确认
                  ↓
用户确认 → 保存六张表快照
                  ↓
删除 A 成功 → 删除 B 失败
                  ↓
停止执行，快照恢复
                  ↓
数据回到这批操作执行前的状态
```

**追问：这和数据库事务有什么区别？（这题答好了是加分项）**

> 数据库事务是“多个修改一起提交，失败撤销未提交部分”。我这里有些操作执行后已经 commit 了，后面失败时不能只 rollback，得用事先保存的快照把数据重新写回去。
>
> 而且我做的是**整表快照回滚，不是逐操作逆向补偿**。因为是故意这么选的：删除的逆操作是重建，id 会变，逐条补偿反而更难保证一致。代价是没有隔离性——恢复期间如果别的请求改了这些表，会被覆盖。

**追问：有什么不足？**

> 三个：执行一半进程突然退出，来不及恢复；别的请求同时改这些表，恢复会覆盖它的修改；确认请求重复到达时没有幂等保护。所以后续优先统一提交边界，再给写操作加幂等键。

**两个范围要记清：**

- 这份备份保护的是**用户这次确认的一批操作**，不是整段聊天里的所有操作。
- 执行后检查发现冲突，当前是**提示用户**，不自动恢复快照。

**记忆词：** 先展示、再确认；执行前整表快照，中途失败就擦回。

### ★★★ 10. 怎么测试和评估 Agent？

**【15 秒版】** 分两层：Mock 模型测框架行为是否确定，真实模型测决策是否正确；判定看最终数据库状态，不看工具调用顺序。

> 分成两部分。
>
> 第一部分测框架本身。用 Mock 模型预先指定每一轮返回什么——先查任务、再改任务，或者故意重复调用工具。然后检查系统是否正确执行、是否触发确认、是否拦住重复调用、失败后是否恢复数据。模型输出固定，所以这类测试每次结果一样。
>
> 第二部分测真实模型的决策能力。给一组固定的用户请求，比如“删除明天下午的会议”，看它能不能选对工具、填对参数、删除前要求确认，最终让数据库达到预期状态，同时记录完成率、错误操作、调用次数和延迟。

**举个例子：**

```
是否先找到正确会议
        ↓
是否在删除前请求确认
        ↓
确认后是否只删除目标会议
        ↓
其他任务和日程是否没被误改
```

**为什么要看最终数据库状态？**

> 同一个任务可以有不同正确路径。有的模型先查全部事件，有的按日期查，只要最后删对了、没越权，就该算成功。所以评测不能要求固定工具顺序，要检查最终业务结果。

**当前做到什么程度（口径必须准）：**

> 内置 5 个基于 Mock 模型的端到端场景，稳定检查工具执行、确认流程和业务状态。它们证明**整条链路是通的**，但**不代表真实大模型的理解准确率**。下一步才是接真实模型、扩请求集、统计成功率和失败类型。

**记忆词：** Mock 测“系统能不能正确执行”；真实模型测“模型能不能做对决定”；数据库状态验证“到底有没有真正完成”。

---

### ★★★ 11. 项目最难的技术问题是什么？

**优先讲“多步写操作部分成功”——这是真实的设计难点：**

> Agent 可能连续执行多个写工具，单步成功不等于整体成功。比如第一个删除完成、第二个失败，用户就拿到一个没预期的中间状态。我因此做了批量确认和执行前快照，失败整体补偿。继续梳理也发现补偿没有原生事务的隔离性，所以后续优先统一提交边界、加确认幂等。

**追问怎么接：** 能定位到 `_handle_confirmation()`、`AgentDatabaseSnapshot.capture()` / `.restore()`，讲清六表范围、删除与恢复顺序，以及为什么 commit 之后还能补偿：**restore 不是 rollback，而是按依赖顺序删六张表的全部行、再按相反顺序重灌快照**，已提交的行也在"删全表"这一步被抹掉。

**这里有一句最值得说的话（真实、且很少有人能说出来）：**

> 这段代码的原注释其实写错了——它说"工具提前 commit 就救不回来"，但测试 `test_restore_rolls_back_partial_insert` 明确验证了 commit 之后仍能恢复成快照状态。因为 restore 走的是删全表重灌，不是 rollback。我后来按测试的实际行为修正了自己的理解。

**为什么这句值钱：** 绝大多数候选人只会复述注释。你说"我的注释和测试矛盾，我发现了，而且我知道哪个对"，可信度直接上一档。

**注意：** 上面是“设计问题”的讲法。具体怎么发现、花多久、线上影响多少，只能按你真实经历补。

### ★★ 12. 为什么自研？如果继续做，最先改什么？

> 当前流程规模可控，自研 Loop 便于直接掌握工具协议、上下文和确认控制；代价是持久恢复、复杂编排这些能力得自己补。接下来优先加强执行层白名单、严格调用预算、确认幂等和统一事务，再建真实模型回归集。如果长任务恢复和复杂分支变成主要需求，我会评估成熟编排框架。

**追问怎么接：** 换框架主要影响编排层，Service、规划器和业务测试可以复用。**不要把“不用框架”包装成“框架不适合生产”**——这是给自己挖坑。

---

### ★★ 13. 同一个确认请求点两次怎么办？

> 当前执行后会删除待确认记录，能避免顺序重复确认；但两个请求同时到达时仍可能重复执行。给待确认操作加执行状态，用数据库条件更新让一个请求原子拿到执行权，再给写操作加幂等键，防超时、重试或崩溃造成重复写入。

**不要混淆：** 调用去重 ≠ 业务幂等；pending 落库 ≠ 并发只执行一次。

> 状态机解决“两个请求同时抢着执行”，幂等键解决“系统不知道上一次到底有没有执行成功”。

---

### ★★ 14. 会话历史放进程内存，多 worker 就安全了吗？

> 不安全，所以我把它从内存里拿掉了。原先的 `Memory` 是个按 session 分桶的 dict，加锁只解决"同一进程内多线程改坏列表"，解决不了多 worker：同一会话的第二个请求落到另一个进程，那个进程的字典是空的，模型看不到上一轮；进程重启也一样，库里明明有记录，两边记忆却不一致。为了补这个洞还长出了 `has_session` / `hydrate` 这一对方法——先问"有没有"，没有再去表里捞，本质上是把缓存一致性问题搬进了业务代码。
>
> 现在每次请求按需从 `chat_messages` 读最近 60 条窗口，进程内不留会话状态：多 worker 天然一致，重启不失忆，也没有锁要维护。顺着这条线把记忆分了三层——层一全量流水只进表不进提示词，层二把溢出窗口折成五段摘要（400 token 封顶）再按 token 卡预算，层三再分规则区、偏好区、事实区，规则区是代码常量模型只读，事实区走候选制（同一事实出现两次才转正确认并注入）。

**追问怎么接：** 代价是每请求多一次索引查询（`session_id` 上有索引），换来的是不需要任何同步逻辑。真正还没解决的是**同一会话的并发写**——两个请求同时发会各自插一条 user 消息，先后由数据库决定；要做严格串行得按 session_id 排队或者加乐观锁，现在没做。

**不要混淆：** 无状态 ≠ 会话串行 ≠ 幂等。读一致了，写仍然可能交错。

---

### ★★ 15. 白名单和提示词能防 Prompt Injection 吗？

> 只能提供部分约束。当前白名单主要限制模型看见哪些工具；要防伪造工具名，还需要执行层检查。外部工具返回的文本必须当数据看，不能改变权限；写操作要有服务端授权、参数校验和必要确认。我会用恶意工具结果和越界调用测试去验证“实际没有执行”。

**不要混淆：** Prompt 指导行为，服务器控制权限。

## 二、8 道高频追问

### ★★ 16. 为什么用 CP-SAT？怎么建模？

> 贪心逐个安排，可能因为早期选择占满关键时间窗而错过更好的组合。CP-SAT 对任务和候选起点建布尔变量，用可选区间和 NoOverlap 表达占用，加前置依赖约束，再最大化优先级、工作量、偏好等加权目标。

**接住两个追问：** FEASIBLE 是可行解，OPTIMAL 才表示模型内已证明最优；5 秒是单次求解预算，外层还有校验重求，不能当请求总耗时保证。

### ★ 17. “时间不重叠但赶不及”怎么检测？

> 普通相邻活动用“下一活动开始减上一活动结束”算可用通勤时间，再和路线估时比较；如果后一段本身就是 travel，就用它的结束时间当最晚到达。地图不可用时标记未校验，不假装通过。

**缓存策略（具体数字背熟，这是细节分）：**

> 路线缓存 5 分钟——路况会变；地点搜索缓存 24 小时；地址解析（geocode）缓存 30 天——地址到坐标几乎不变。三种数据变化频率不同，所以 TTL 分开设。

**进一步追问：** 路线是估时，不是到达保证；外部校验应该有最终合法性出口。

---

### ★★ 18. 项目需不需要 RAG、MCP、多 Agent？

> 当前数据是任务、日程、偏好这类结构化状态，直接查库即可。有了大量历史邮件或文档后，可以用 RAG 定位证据；需要标准化接入外部工具或向其他客户端开放能力时，可以加 MCP；只有子任务能独立分工、收益超过协调成本时，才考虑多 Agent。当前 Skill 不是独立 Agent。

**核心态度：** 从业务瓶颈决定架构，不为关键词加组件。

### ★★ 19. 线上怎么定位错误、控制成本？

> 当前记录工具阶段、状态、耗时、模型 token 和估算费用，能回看失败步骤。进一步要按 run_id、step_id、tool_call_id 关联模型与工具调用，记录错误分类、重试和脱敏参数，并建立请求总 deadline 与 token/费用预算。

**可以补一句硬账（显得真算过）：** 单次模型调用超时默认 30 秒，12 轮迭代理论上限就是 6 分钟，而当前**没有请求级总 deadline**——所以最坏情况是慢，不是错。这是我要补的第一块。

**不要混淆：** 可观测 ≠ 可恢复；费用估算 ≠ 精确账单；次数预算 ≠ 延迟预算。

### ★★ 20. 有真实用户和效果数据吗？怎么证明项目价值？

## 三、4 个能主动加分的深度点（v2 新增）

> 这几题面试官大概率不会直接问，但**你自己讲出来就是加分**——它们证明的不是“我实现了功能”，而是“我知道为什么这么设计”。

### ★★ 21. 为什么快照只备 6 张表，不是全部 13 张？

项目一共 13 张表：`tasks`、`events`、`task_dependencies`、`schedules`、`user_preferences`、`plan_versions`、`agent_runs`、`chat_messages`、`pending_actions`、`saved_locations`、`evaluation_runs`、`session_summaries`、`memory_facts`。

> 备份的是前 6 张，也就是用户能感知到的业务状态。另外 7 张是执行轨迹、会话、审计和评测数据——**回滚它们反而错**：如果一次失败的操作把审计也擦掉，你就再也查不到“刚才到底发生了什么”。而且地点库和评测数据跟这次写操作没关系，没有回滚的必要；后加的两张派生表（会话摘要、长期事实）是从对话推出来的，丢掉重算就有，更不该进快照。

**追问“那 pending_actions 不备会不会漏”：** 待确认记录本来就是执行完即删的，它的生命周期在快照范围之外，靠状态机和幂等保护，不靠回滚。

**这一题的价值：** 它证明你分得清“业务状态”和“审计状态”。很多人的事务实现是不加区分地全备。

---

### ★ 22. 时间怎么建模？“明天下午”落库成什么？

> 任务存的是预计时长和截止时间，日程存的是具体日期加起止时刻，两者分开——因为“要做什么”和“什么时候做”是两件事，一个任务可能对应多段日程，重排时只换日程不动任务。
>
> 模糊表达（“明天下午”）由模型结合当前时间和偏好解析成具体时刻再落库，而不是存一个“下午”的字符串。代价是解析错了用户要能看出来——所以确认和展示环节必须显式给出解析结果。

**追问“跨时区怎么办”：** 当前按本地时区处理，没有做时区字段和 DST 处理，这是明确缺口。真要做，需要日程存绝对时刻 + 时区，任务存浮动语义。

---

### ★★ 23. 一次请求最坏要等多久？

> 单次模型调用超时 30 秒，迭代上限 12 轮，理论上限 6 分钟。加上 CP-SAT 单次求解预算 5 秒、外层还有校验重求，一次复杂排期的真实耗时在十几秒量级。
>
> 当前**没有请求级总 deadline，也没有流式输出**——前端只能等一个完整响应。这是体验上的最大短板：用户点完不知道系统在干什么。要改的话，先加总 deadline 让慢请求提前失败，再加 SSE 把“正在查任务 / 正在求解 / 正在校验”这些阶段推给前端。

**说这段的好处：** 你自己把最难看的地方算清楚了。比被问出来强十倍。

---

### ★★ 24. 补偿事务能撤销已提交的写入吗？

> 能撤销，但机制必须讲准，否则会被听成"我在糊弄"。
>
> `restore()` 的第一步是 `rollback()` 丢掉未提交改动，然后是**按外键顺序删除六张表的全部行**，再按相反顺序把快照重灌进去、commit。所以即使某个工具中途自己 commit 过，它的写入也会在"删全表"这一步被抹掉。这一点有测试：快照后新增一行并 commit，restore 之后仍然只剩快照里那一行。
>
> 代价是这不是事务，是**整表覆盖式回滚**：没有隔离性，恢复期间别的请求写这几张表会被覆盖；进程崩在"已提交但尚未补偿"的窗口里就没人来恢复；六张表之外的副作用（外部日历、发信）不在覆盖范围内。

**追问"那还要不要统一事务"：** 要。整表覆盖在单用户本地规模下够用，但它的成本随表总数据量增长，隔离性为零。方向是 Service 只 flush、外层统一 commit，外部副作用单独做幂等。

**顺带一个诚实的细节：** `transaction.py` 里有个 `ToolCommitNotAllowedError`，本意是禁止工具 commit，目前没有接入运行时。但既然 commit 也能被快照覆盖，这条约束的实际优先级比我最初以为的低——这也是我后来才想明白的。

**这一题的真正价值：** 你分得清"整表覆盖"和"事务"的区别，也知道自己的机制在哪一层失效。

## 四、3 道防守题（v2 新增，会被直接问）

### ★★ 25. “本地优先”和调云端 LLM 不矛盾吗？

见 §0.1，完整背这段：

> 本地优先指数据在本地 SQLite、排期计算不依赖模型、模型层可整体换成本地 Ollama 或 vLLM。默认配云模型是部署选择——本地模型质量不够，但架构上随时能切回完全离线。我做的抽象层就是为了这个：换 provider 只改配置，不动业务代码。

---

### ★★ 26. 用户话说一半、缺参数怎么办？

**诚实版（推荐）：**

> 当前没有结构化的澄清机制——没有 `ask_user` 这类工具，缺参时只能靠模型在自然语言里反问，或者它自己猜一个默认值继续。这是我最想补的一块。
>
> 正确做法是工具参数区分 required 和 optional，缺 required 时中断循环、生成一张澄清卡片让用户填，而不是让模型自由发挥。判断标准应该是“缺的字段会改变执行结果”——只影响展示的可以不问，影响写操作必须问。

**这一题的隐藏价值：** “Agent 什么时候该停下来问”是产品化的分水岭。你主动承认没做，比说“模型会自己问”可信得多。

---

### ★★ 27. 模型传错参数、编出不存在的 id 怎么办？

> 参数校验在工具层做，失败不抛异常，把字段级错误结构化回传给模型，让它下一轮自己修正；工具名不存在直接拒绝并回传可用列表。
>
> 但当前没有“同一工具连续错两次就放弃”的止损，靠的是调用预算和轮数上限兜底。更稳的做法是给每个工具加失败计数，超阈值就从可见列表里摘掉。

## 五、已知缺口清单（面试官问“还有什么不足”时照这个答）

|---|---|---|

## 八、最后必须记牢的口径

| 可以有力度地说 | 追问时要讲清 |
| --- | --- |
| ReAct 多步循环（自研） | 动作由原生 Function Calling 表达，不是文本解析 `Thought/Action` |
| 本地优先 | 数据/计算/模型层都可本地，默认云模型是部署选择 |
| 37 个工具、10 个 Skill | Skill 不是多 Agent，白名单未做执行硬隔离 |
| 上下文与记忆管理 | 字符裁剪 + 文本恢复，不是长期语义记忆或执行恢复 |
| 模型分类降级与调用预算 | 能力有降级，总调用阈值不是逐次硬上限 |
| 多步确认与补偿事务 | **能撤销已提交的写入**（delete 全表 + 重灌），但不是事务：无隔离、无崩溃原子性 |
| `ToolCommitNotAllowedError` | 只是预留类型，未接运行时；且 commit 本来也能被快照覆盖，优先级不高 |
| 执行后审计与计划撤销 | 审计当前告警；撤销不是通用数据回收站 |
| 270 个测试方法、5 个评测场景 | 场景用 Mock，不是线上模型成功率 |
| CP-SAT 全局优化 | 可行解 ≠ 已证明最优，总时延不止一次 Solve |
| 参数校验与错误回传 | 无失败计数止损，靠调用预算兜底 |
| 澄清能力 | 无结构化 ask_user，靠模型文本反问 |

**最值得反复练的一句话：**

> 我不仅知道 Agent 怎么选工具，也能解释它什么时候该停、哪些操作要确认、失败后留下什么状态，以及怎么验证这些行为。
